## Intent

Establish the deterministic core the whole factory depends on, with no I/O. Every later Wave 1 BIU plugs adapters into these rules rather than reinventing them, so lifecycle, release, scheduling and admissibility decisions have exactly one owner and are testable without a provider, a network or a database.

This is S1 of Wave 1: the first behaviour after PY-01's structural skeleton.

## Binding rules — not delegated

1. Pure domain only. No file, network, database, subprocess, clock or randomness access. Time, identity and randomness enter through port-shaped parameters supplied by callers, never imported directly in `domain/`.
2. Lifecycle vocabulary is fixed by Authority §9: CAPTURE, SPECIFY, PLAN, TASKS, READY, IMPLEMENT, VERIFY, REVIEW, ACCEPT, DONE. This BIU owns IMPLEMENT onward. There is no MERGE state. Cancellation and authority blocks are exceptional outcomes, not an eleventh happy-path state.
3. AlienIntent never computes or invents product priority. Priority is an input value carried from the Work Management snapshot.
4. A worker self-report is an observation. Only policy evaluation over definitions and trusted observations produces a verdict.
5. The module lives under `src/alienintent/execution_coordination/domain/` per PY-01 layering. Configuration is not read outside `composition/`.

## Scope

1. **BIU contract value model**, versioned and content-digest identified, covering the plan's contract fields and the work-and-release BIU record: intent; satisfied requirement IDs; fixed decisions; boundaries/authorized scope and exclusions; dependencies; required capabilities; budget and retry policy; completion criteria; verification obligations; required evidence; non-goals; candidate custody requirements; release policy; authority issuer and references; target repositories and baselines; required closure actions; stop/escalation conditions. Construction validates invariants and rejects an incomplete contract with a typed error.
2. **Release and admission rules.** A release binds an exact BIU contract version/digest with its authorization provenance, whether the source is automatic policy (ON) or an explicit human release (OFF). Readiness, dependency satisfaction, capability availability and budget availability are checked before admission. Repeated release of the same identity is idempotent; the same identity with a changed payload is a conflict. READY alone never admits execution.
3. **Execution lifecycle state machine** for IMPLEMENT → VERIFY → REVIEW → ACCEPT → closure → DONE, with rework returning to IMPLEMENT and invalidating a prior acceptance, expected-version guards on every transition, and distinct terminal/exceptional outcomes for cancellation and authority block.
4. **Candidate custody guard.** VERIFY is inadmissible unless the contract's candidate identity is present and marked durably retrievable. The mechanics of proving retrievability belong to PY-06; this BIU owns the guard and its typed rejection.
5. **Scheduling policy** as a pure function over a supplied candidate set: eligible items are released-or-releasable, dependency-satisfied and within capacity; ordering is declared priority first, then FIFO among equal or absent priority; blocked items are skipped without blocking independent work. Capacity limits are expressed for global, profile and repository scopes, defaulting to one active mutating stream per repository, with verifier (non-mutating) invocations excluded from the mutating limit but counted against global capacity.
6. **Verdict admissibility rules** separating definition, observation and verdict.
7. **Architecture fitness extension** in `tools/fitness/`: a check that `domain/` and `application/` do not import wall-clock, randomness or identifier-generation facilities directly, demonstrated failing on a violating fixture and passing on the tree.

## Non-goals / excluded

Persistence, stores, SQL, event ingress, GitHub or any vendor adapter, worker invocation, worktrees, CLI, HumanDecisionRequired payloads and inbox (PY-07), doctor, projection, cost/routing learning, Requirements IR or any Wave 2+ capability. No Node source, test, configuration or runtime change. No FactoryChecks change. No credentials, deployment or provider spending. No Python Sovereignty claim.

## Acceptance criteria

1. The contract model exists with every field above, validates invariants, and produces a stable content digest such that a changed payload changes the digest.
2. Release/admission rules reject: a missing or stale readiness reference, an unsatisfied dependency, a missing required capability, an absent hard-required budget dimension, and a conflicting payload for an existing release identity. Duplicate identical release is idempotent.
3. The lifecycle state machine rejects every transition not permitted by Authority §9 semantics, enforces expected-version guards, returns to IMPLEMENT on rework with the prior acceptance invalidated, and distinguishes an authority block from a failure.
4. VERIFY is refused when candidate identity is absent or not marked retrievable, with a typed rejection.
5. Scheduling tests demonstrate: priority order honoured; FIFO among equal and among absent priority; a blocked dependency skipped while independent work proceeds; WIP saturation withholding admission; a verifier invocation not consuming the mutating slot.
6. A worker claim of success cannot produce ACCEPT without policy evaluation over required evidence.
7. The new fitness check fails on a violating fixture and passes on the tree, preserving real exit status. All PY-01 fitness checks still pass.
8. The Node bootstrap is byte-identical and `node scripts/check.mjs all` still passes.

## Verification requirements

- Executable proof: deterministic unit and table-driven tests for every rule above, run in a clean environment with real exit statuses retained.
- Both directions for each fitness check: violating fixture fails, tree passes.
- Node suite executed and passing (EOS rule 1).
- Evidence retained with the invocation: test output, fitness output on both fixture and tree, Node suite result.

## Capabilities and budget

Capabilities: repository workspace, Git, Python toolchain, local test execution. No network, no credentials, no deployment.
Budget per SWF-09: hard wall-clock duration, attempts, retries, concurrency and cancellation; token and monetary cost measured where the provider reports them and never assumed zero. No hard token or monetary ceiling is required by this BIU.

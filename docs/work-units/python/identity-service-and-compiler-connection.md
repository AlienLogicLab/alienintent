## 0. The whole design (plain English)

A work item is **one row in one table** in the project's SQLite database file. The row holds, kept separate:

- the **permanent identifier** (`id`): an existing name such as `PY-09` or `WO-000005`, kept exactly; or, for genuinely new work, a UUID from the standard library;
- a **creation-request reference** (`request_ref`): one short, stable string the creator supplies so the same request is never registered twice — `requirement:<id>` from the compiler, `packet:<repository>/<path>` for a hand-written packet, `issue:<n>` for imported work, `legacy:<name>` for migrated names. It is not a hierarchy and never encodes a label or a parent;
- a **human-readable label** (`label`), unique;
- an **optional parent identifier** (`parent_id`): empty for independent work; the real parent when work was split;
- the **workflow state** and the **packet pointer**: repository, path and exact Git commit of the packet as currently registered (authorization is the state and the evidence references, set by later units); and references to **assessment, approval and verification evidence**, each of which names the exact commit it was made against (the second child fills these; this unit creates the columns).

Git keeps the packet text and every revision of it. Workflow evidence — assessment attempts, approvals, verification — stays in the evidence repository as today, durable, and keeps what was assessed, approved, attempted and verified against which exact revision. The database keeps the row and nothing that duplicates either: no packet text, no packet history. **The pointer is verified, not trusted:** before a pointer is stored, the adapter retrieves `<commit>:<path>` from the repository and refuses unless the retrieved bytes are exactly the instructions being registered — a commit where implementation starts is not the commit that holds the packet, and a digest alone proves no such link. Editing a packet makes a new commit; it does not move the row's pointer and authorizes nothing. Before assessment or approval — while the row is at `CAPTURE` — a recompile may update the saved instructions and their Git reference; once the row leaves `CAPTURE` this unit refuses that change (`POINTER_PRESENT`), and moving the pointer then is a controlled operation of a later unit, with renewed assessment and approval.

The database's own uniqueness rules and transactions give the rest: a repeated request returns the existing row, after a crash and when two processes ask at once, because the unique index refuses a second row and a transaction either happens or does not. Nothing numbers, counts, limits or rebuilds anything.

**Design basis (Founder, 2026-10-01):** standard library, existing project tools, the database's transactions and uniqueness, the fewest parts; Git for text and history; every extra mechanism must prevent a demonstrated failure.

After this unit: (a) `register(request_ref, label, kind, parent_id=None, pointer=None)` returns the same row for the same `request_ref`, called once, twice, after a crash, or from two processes at once; (b) every existing name is a row with its owner and is never reissued; (c) the compiler obtains identifiers from the service before it compiles and never compiles over an unmigrated assignment; (d) a retired row keeps everything; (e) a row that carries a packet pointer points at a commit that exists, holds at `path` exactly the instructions that were registered, and is reachable from a retained ref; (f) a compiler-generated packet is in Git before its row exists; (g) the database holds no packet text or history, and existing evidence records are untouched; (h) `import_completed` records previously completed work once, at `DONE`, with exactly its real evidence, through this same service.

## 5. The row (domain rules in `domain/work_identity.py`; constraints in the adapter's `CREATE TABLE`)

| Column | Rule |
| --- | --- |
| `id` | primary key; an existing name matching the grammar, or a UUID (36 characters, version 4); never recycled |
| `request_ref` | unique, non-empty; `<kind>:<value>` with `kind` in the closed set `requirement` (the compiler), `packet` (a hand-written packet: `packet:<repo>/<path>`), `issue` (an import), `legacy` (migration); `value` must match the kind's own format (`requirement`: the `<id>` the compiler just reserved, checked by construction, never operator-supplied; `packet`: `<repo>/<path>` where `repo` is a name in the project's repository configuration and `path` is non-empty; `issue`: a positive decimal integer; `legacy`: an existing name matching the identity grammar) — any other kind, or a value that does not match its kind's format, is refused `INVALID_REQUEST_REF` naming the kind and value; the value is a location or number, never a label or a parent |
| `label` | unique, non-empty |
| `parent_id` | nullable; foreign key to `work_item(id)`; `CHECK(parent_id IS NOT id)` |
| `kind` | `REQUIREMENT`, `BIU`, `MAINTENANCE`, `DECISION`, `MIGRATION` (formal design 6.1) |
| `state` | the 6.1 lifecycle state; `CAPTURE` on registration; `DONE` when a row is created by `import_completed` as an explicitly authorized historical record (not a transition); after creation it changes only through `set_state`, which accepts only a row of the legal transition table |
| `retired_at` | nullable timestamp; set once |
| `repo`, `path`, `commit` | the packet pointer: repository (a name from the project configuration, which maps it to a local clone and names its retained refs), path within it, 40-hex commit of the packet itself; all three set or all three null; stored only after the adapter has retrieved `<commit>:<path>` and found it byte-equal to the instructions being registered |
| `assessment_ref`, `approval_ref`, `verification_ref` | nullable references to evidence records in the existing evidence repository (its `Ref`), which remain durable there; each names the exact commit it was made against; written by later units and by import |
| `created_at`, `updated_at` | set by the adapter |

Constraints: `PRIMARY KEY(id)`, `UNIQUE(request_ref)`, `UNIQUE(label)`, the foreign key with `PRAGMA foreign_keys = ON` on every connection, the check. No row is ever deleted; no column is ever rewritten except `state`, `retired_at`, `updated_at`, the three evidence references, `request_ref` from `legacy:<name>` to `requirement:<id>` by migration only (the repair for a profile omitted from an earlier run), and the pointer — by `set_pointer` only while the row is at `CAPTURE`, and past `CAPTURE` by the later controlled operation only.

## 6. Service, port, adapter, composition, migration, compiler

- **Port** `WorkItemRepository`: `transaction()` (context manager: `BEGIN IMMEDIATE` … `COMMIT`, or `ROLLBACK` on any exception), `register(...)`, `retire(id)`, `find(id_or_label)`, `children(id)`, `set_evidence(id, which, ref)`, `set_state(id, state)` (the only way a row's state changes after creation: refuses `ILLEGAL_TRANSITION` unless the pair (current state, new state) is a row of the legal transition table, formal design 7.3; these two units do not call it), `import_completed(request_ref, label, kind, pointer, evidence)` (see the service), `commit_packet(repo, path, bytes, existing_pointer) -> commit` (no history walk: if the row's existing pointer retrieves bytes equal to the given bytes, that commit is returned; else if the blob at the packets branch head, `<packets branch>:<path>`, is byte-equal, the head commit is returned — it contains the path at those bytes and is on a retained branch; else the adapter writes the bytes to the packets branch without touching the profile's working tree — plumbing or a separate worktree, the PRODUCER's choice — and returns the new commit; a packets branch that does not exist yet starts from the default branch; every step is one object read or one commit, independent of how many commits the branch holds), and `set_pointer(id, pointer)` (if the row already has a pointer: succeeds when its bytes equal the given bytes; replaces it when the row's `state` is `CAPTURE` — a registered-but-unauthorized packet may follow a recompile, which authorizes nothing because authorization is the state and the evidence; refuses `POINTER_PRESENT` when the state is past `CAPTURE` — changing authorized instructions is the later controlled operation); each usable inside a `transaction()` or wrapped in its own.
- **Service** `WorkIdentityService` (application): `register(request_ref, label, kind, parent_id=None, pointer=None) -> WorkItem`, where `pointer = (repo, path, commit, instructions: bytes)`, always creates the row at `CAPTURE` — inside `transaction()`: when a pointer is given, the adapter runs `git show <commit>:<path>` in the configured clone and refuses `POINTER_MISMATCH` unless the output is byte-equal to `instructions`, and `git merge-base --is-ancestor <commit> <retained ref>` for the repository's retained refs, refusing `COMMIT_NOT_RETAINED` otherwise; nothing is written on either refusal; then `INSERT … ON CONFLICT(request_ref) DO NOTHING`, then `SELECT … WHERE request_ref = ?`; the existing row is returned as it is (pointer, state and retirement included — a repeat never changes a row). `LABEL_IN_USE` (unique index) and `PARENT_NOT_REGISTERED` (foreign key) roll back. Two processes are serialized by SQLite's write lock (5-second default timeout, then a typed error and rerun). The service holds no state and generates nothing. `set_state(id, state)`: inside one `transaction()` (`BEGIN IMMEDIATE`, so a concurrent writer waits), read the row's current state, refuse `ILLEGAL_TRANSITION` unless (current, new) is a row of the formal design 7.3 table, then `UPDATE … SET state = ? WHERE id = ? AND state = <the state just read>`; the database's single-writer lock means two concurrent calls are applied one after the other, each against the state the other left. `import_completed(request_ref, label, kind, pointer, evidence) -> WorkItem` records previously completed work as an explicitly authorized historical record: only the operator's `work import` command calls it; `request_ref` must be of kind `issue`; inside one `transaction()` it runs the same pointer checks as `register`, then `INSERT … ON CONFLICT(request_ref) DO NOTHING` with `state = DONE` and exactly the evidence references the operator gives (possibly none), then reads the row back; it invents no workflow step, assessment or approval and does not call `set_state` (no transition happened); a repeat returns the existing row unchanged.
- **Adapter** `adapters/work_item_repository.py` (declared owner of `work_item`): `sqlite3.connect(path, isolation_level=None)`, `PRAGMA foreign_keys = ON` on every connection, `CREATE TABLE IF NOT EXISTS` at open, `uuid4()` ids, SQLite `strftime` timestamps, the `git` subprocess calls; a `POINTER_MISMATCH` message says "bytes differ" and names the path; an unexpected failure of any `git` subprocess call (a corrupted clone, a missing binary, an I/O error) is `GIT_READ_FAILED`, naming the command and path, and rolls back like any other refusal. The retained-reference lookup is bounded to three direct checks and never lists or searches tags: `git merge-base --is-ancestor <commit>` against the default branch, then against the packets branch, then against the single tag `work/<id>` of the row being checked, looked up by its exact name (a row being registered for the first time has no tag yet, so for it only the first two can succeed); a ref that does not exist — the tag before it is first set, or the packets branch before the first compile — is a plain miss, found by `git rev-parse --verify --quiet <ref>` before the ancestor check, never `GIT_READ_FAILED`; if none contains the commit, `COMMIT_NOT_RETAINED`. **The tag `work/<id>`** is owned by this adapter, the component that saves packets and their references: whenever it stores a pointer (`register` or `import_completed` with a pointer, or `set_pointer`), it records the tag write and `transaction()` performs it only after the outermost `COMMIT` succeeds (so the compiler's caller-held transaction tags nothing until it commits, and a rollback tags nothing), setting `work/<id>` to that commit in the configured clone (`git tag -f`, a no-op when already equal). Every successful call that leaves a row with a pointer — a repeat of `register` or `import_completed`, and `set_pointer` with equal bytes — re-applies the tag, so a crash between the database commit and the tag is repaired by the next such call; in the meantime the commit is still retained by the branch that passed the check, and compiler pointers are always on the packets branch, which is never deleted. The tag keeps the pointed commit retrievable even if every branch that held it is later deleted. It is never deleted; it moves only when `set_pointer` replaces a pointer at `CAPTURE`. It grows by at most one tag per row with a pointer, is retained for the project's lifetime like the row, and is published to the remote by the publishing rule below. The project configuration maps each repository name to **one configured clone per project**, which every profile, the compiler and the second child use; it is fetched by the existing profile setup, not by this unit. **The packets branch** is owned by this adapter on behalf of Work Preparation; it grows by one commit per changed unit per compile and by nothing else; it is retained for the project's lifetime and is published to the remote by the publishing rule below. There is no existing local-clone disk-pressure error type in the codebase to reuse (checked: nothing resembling it exists); under disk pressure in the clone this adapter raises a new typed error, `CLONE_UNAVAILABLE`, naming the clone path — the compile holds and nothing is deleted or rewritten automatically; reclaiming space is an operator action on the clone.
- **Publishing** (in the existing publishing file, `invocation_runtime/adapters/git_source_control.py`, and its port `invocation_runtime/ports/source_control.py`, both added to this unit's permitted files because local-only storage is not durable): a new method beside the unchanged `publish_and_read_back`, `publish_refs(clone: Path, remote: str, refs: tuple[PublishRef, ...]) -> None`, where `PublishRef = (ref, commit, force)` is a small frozen dataclass in the port module and `PublicationFailed` (`PUBLICATION_FAILED`) is the port's typed error. The adapter knows nothing about rows or states: it pushes exactly the given refs from `clone` to `remote` (`git push <remote> <commit>:<ref>`, with `+` only when `force` is true) — never `--tags`, `--mirror` or a wildcard — then runs `git ls-remote <remote>` for exactly those refs and returns only if each points at its `commit`; any push or read-back failure raises `PublicationFailed` naming the refs. **Every operation that saves a packet reference publishes through this one method** — no other code pushes these refs. `work/<id>` is a lightweight tag, so the remote tag names the commit itself: pushing `<commit>:refs/tags/work/<id>` sends that exact commit and its history to the remote, the remote tag keeps it reachable there, and the read-back must show the remote tag at exactly that commit. `register` and `import_completed`, when they store or return a row with a pointer, call `publish_refs` after their transaction and tag step with that row's tag (`force` true only while the row is at `CAPTURE`); a failure raises `PUBLICATION_FAILED` after the row is committed — the row exists, unpublished — and a repeat of the same call, which returns the existing row, sets and publishes the tag again, so a failed push is retried simply by repeating the request. `set_pointer` is called only by the compiler in this unit; any later caller must publish the same way. **The compiler batches:** right after its pointer transaction commits and the tags are set, and before `_persist`, it calls `publish_refs` with the clone and remote named by the project configuration and the refs it already knows — the packets branch at its head (`force` false; the branch only grows) and each candidate unit's `work/<id>` at its row's commit (`force` true only for a unit whose row it read at `CAPTURE` in that transaction, since only such a tag can have moved). A `PUBLICATION_FAILED` makes the compile hold before `_persist`; the rerun reaches the same pointers and tags and calls `publish_refs` again. Retrying is safe: refs the remote already holds at the same commits change nothing, and after a partial failure the retry completes the rest. Existing callers of `publish_and_read_back` are unchanged. Composition injects the port into `WorkIdentityService` and the compiler service; this adds the first `context_assembly` → `invocation_runtime` edge, and since `invocation_runtime` imports nothing from `context_assembly` it forms no cycle and, under the fitness rule, needs no coupling-register entry.
- **Composition** `composition/work_registry.py`: opens the one project database file named by the project-level configuration entry, which also maps repository names to local clones and lists the project's configured profiles with each profile's own operational database path (every profile keeps its own `state.sqlite`; `composition/offline_profile.py` line 176), and hands the repository and, to the compiler, a read-only `SQLiteOperationalStore` opened on each configured profile's file, since one profile's store cannot see another's.
- **Migration** (`work migrate --snapshot <doc> --profile <name>…`), additive and repeatable: one transaction; for every name in the compiler's `identity_snapshot` (`active`, `retired`, `reserved`) and every listed profile's `upstream:identity-reservations` record: `id = label = name`, `kind = BIU`, `state = CAPTURE`, `request_ref = requirement:<id>` when a record maps the name, else `legacy:<name>`, `retired_at` for `retired` names, no pointer. A present row with the same values is skipped; a `legacy:` row that a later input maps is re-keyed to `requirement:<id>` and reported; any other difference, one name under two keys, one key with two names, or a record from another project → `ROLLBACK`, `MIGRATION_CONFLICT` naming both sources. The reservation records stay as history, are never written again, and are read only by `work migrate` and by the compiler's check below.
- **Compiler** (`initial_compilation_service.py`): before `compile_initial`: read the `upstream:identity-reservations` record of **every configured profile of the project**, each through the store port against that profile's own operational database (`read_state(<profile>, RESERVATIONS)` on the read-only store composition opened for it; one read per profile, each against that profile's own `state.sqlite` file, separate from the project database and from each other — these reads are sequential and not held under one lock together, since migration is a one-time, operator-run step and not a case this design treats as concurrent; the current profile's store cannot see the others, so reading other names through it would find nothing and pass falsely); for every requirement of the design that any of those records maps to a name, the table must hold that name with `request_ref = requirement:<id>` (one `SELECT` each) — else hold `MIGRATION_INCOMPLETE` naming the requirement and the profile, nothing registered. Only the registration itself is transactional: an identifier is issued for a requirement only after every configured profile's old assignment for it has been checked, inside one `transaction()` on the project database that covers `register("requirement:<id>", "requirement:<id>", "BIU")` for each requirement, **without a pointer** (the packet does not exist yet); a retired row → hold `IDENTITY_RETIRED`. After `compile_initial` yields a candidate and before `_persist`, **one write transaction** covers the permission check and every pointer write, so no row's `state` can change between them and either every unit's pointer is written or none is: `BEGIN IMMEDIATE`; read every unit's row; serialize each unit's contract and text canonically (`canonical`, `compilation.py` line 58); for every unit whose row has a pointer and a `state` past `CAPTURE`, compare those bytes with `git show` of the pointer — any difference → `ROLLBACK`, hold `POINTER_PRESENT` naming the unit, nothing committed to Git, nothing persisted, no pointer touched (changing authorized instructions is the later controlled operation); then, still inside the transaction, for each unit `commit_packet(repo, "<packets directory>/<id>.json", bytes, the row's pointer)` — the row's own commit when its bytes are unchanged, the branch head when it already holds them, a new commit otherwise — and `set_pointer(id, (repo, path, commit, bytes))` with the same byte comparison and retained-ref check as `register`; `COMMIT`. The Git calls run while the database write lock is held; they are small and bounded (at most the three ancestor checks per unit, plus one object read or one commit), but they serialize behind the one project database's lock project-wide, so a registration or compile anywhere in the project can wait on another's Git calls — accepted latency, not a silent failure: a writer that cannot get the lock within the busy timeout surfaces the existing typed lock error and reruns, the same as any other contended write. **Git is not rolled back:** if the process dies after some `commit_packet` calls and before `COMMIT`, the database holds nothing and the packets branch holds commits no row points at; that is harmless because the branch is append-only history — the rerun's `commit_packet` finds equal bytes and returns the same commits, and a later recompile with different bytes simply leaves the earlier commit as an unreferenced revision. So the row points at the commit that holds the packet, never at the baseline, only after Git has it, and only together with every other unit of the candidate. A held compile — including a `POINTER_PRESENT` hold — commits nothing. Pass the key→id map to `compile_initial` as `reservations`; `_reserve` keeps its grammar check and reduces to "every key takes the id the map gives it" (numbering, collision and exhaustion branches deleted; `IDENTITY_RULE` → `INITIAL_IDENTITY_REGISTRATION_v2`; the candidate's `reservations` field holds the id map). Ids are final before the compile runs, so every digest the compile derives is final; `_persist` is unchanged and the evidence it retains stays where it is; a crash at any point reruns to the same candidate, the same pointer per unit (`commit_packet` reuses the row's own commit when the bytes are unchanged, so an interrupted multi-unit run leaves every already-pointed unit where it was) and the same pointers (`set_pointer` succeeds on equal bytes); a `PERSISTENCE_CONFLICT` hold in `_persist` leaves rows with pointers and the rerun passes through them the same way. The reservation aggregate is never written again. `identity_policy` and `identity_snapshot` remain required inputs as `_limits` checks them (lines 85–93) and `identity_snapshot.active` still feeds `validation_stages`; neither influences allocation. `identity_valid` accepts a UUID regardless of policy and never a letter suffix on one; `_validate_split` (`compilation.py` line 554) and the grammar tests follow; the Node runtime and its contract documents are untouched.

## 7. Growth and retention

One row per piece of work ever registered by a human action, a compile or the one-time migration; no automatic loop creates rows; retained for the project's lifetime (formal design 6.1A); never deleted. Packet text and history live in Git (the packets branch's owner, growth, retention and pressure response are in section 6); assessment, approval and verification evidence lives in the evidence repository exactly as today and stays durable there (the compiler's retained candidate record, which contains the compiled contracts, is such evidence and is kept); the database duplicates neither.

## 8. Sequences

**`register`**: `BEGIN IMMEDIATE` → (pointer given: `git show` byte comparison, retained-ref check) → `INSERT … ON CONFLICT(request_ref) DO NOTHING` → `SELECT` by `request_ref` → `COMMIT`.
**`work migrate`**: read inputs → `BEGIN IMMEDIATE` → per name: insert if absent, else compare, re-key `legacy:` when mapped, any other difference → `ROLLBACK` → `COMMIT`.
**Compiler**: `BEGIN IMMEDIATE` → every configured profile's old assignments present? → register requirements (no pointer) → retired? → `COMMIT` → `compile_initial(…, reservations = id map)` → candidate: `BEGIN IMMEDIATE` → read rows, compare bytes against the pointers of units past `CAPTURE` (`ROLLBACK` and `POINTER_PRESENT` hold, nothing written) → `commit_packet` and `set_pointer` for each unit → `COMMIT` → tags set → `publish_refs` (packets branch and the units' `work/<id>` tags; `PUBLICATION_FAILED` holds) → `_persist`.

## 9. Behavior after each relevant completion

Same request → the same row, unchanged. Same compile → the same ids and candidate. Migration again → no change or a reported re-key. Retire → `retired_at` set; `parent_id` and `children(id)` unchanged; `register` with that `request_ref` → the retired row. A new commit of a packet → nothing in the table changes.

## 10. Restart and missed-signal recovery

A crash inside any database transaction leaves nothing in the database; a rerun gives the same result as an uninterrupted run. Git commits made inside the compiler's pointer transaction survive a crash as unreferenced revisions on the append-only packets branch; the rerun reuses them when the bytes are equal and otherwise leaves them as history. No pending state, no marker, no manual reset.

## 11. Failure behavior

`LABEL_IN_USE`, `PARENT_NOT_REGISTERED`, `POINTER_MISMATCH`, `COMMIT_NOT_RETAINED`, `MIGRATION_CONFLICT`, `ILLEGAL_TRANSITION`, `INVALID_REQUEST_REF`, `GIT_READ_FAILED` → rolled back, nothing written, the reason names the value or the failed command and path. `IDENTITY_RETIRED`, `MIGRATION_INCOMPLETE` → compiler holds, nothing compiled, nothing registered; `POINTER_PRESENT` → compiler hold, nothing persisted; `CLONE_UNAVAILABLE` → compiler holds, nothing deleted or rewritten. `PUBLICATION_FAILED` → `publish_refs` names the refs and nothing is reported as published; from the compiler it holds before `_persist`; from `register` or `import_completed` the row is already committed and a repeat of the same request publishes it; every rerun is safe. Database locked beyond the timeout → typed error, rerun. Nothing else can fail.

## 12. Permissions and prohibited actions

Permitted: sections 13–14. Prohibited: any second creation path or any write to `work_item` outside its adapter; per-profile tables; numbering; deleting rows; rewriting `id`, `label`, `parent_id` or `kind`, or `request_ref` other than the migration re-key; moving a pointer of a row past `CAPTURE` (a later unit); storing a pointer whose commit does not hold exactly the registered instructions; recycling a name; storing packet text or packet history in the database; touching existing evidence records; `uuid`, `datetime`, `time` or `subprocess` in domain or application code; GitHub API reads or writes (the Git pushes of the publishing rule are the only remote writes); pushing with `--tags`, `--mirror` or a wildcard refspec; any change to the Node runtime.

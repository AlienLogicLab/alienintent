## Doctor semantics (SWF-13, confirmed)

Founder decision SWF-13 confirms the fail-closed interpretation for Wave 1: every doctor prerequisite listed as required is hard-required; FAIL blocks autonomous start; UNAVAILABLE also blocks autonomous start; FAIL and UNAVAILABLE remain distinct outcomes; there is no degraded-autonomy mode. The exit-code distinctions below are preserved. No further Founder decision is required on this point.

## Intent

Refuse to start autonomous work on a broken installation. Before the factory runs unattended, every dependency it will rely on is validated: configuration, work-management access and mapping, source control, provider readiness, transport, persistence and execution capability.

## Architecture references

- **Architecture Authority** §35 observability, §36 doctor/diagnostics, §38 installer/bootstrap UX (health checks), §31 configuration, §32 secrets, §34 upgrade/compatibility preflight.
- **SWF-13** — confirmed fail-closed doctor semantics for Wave 1.
- **SWF-04** — installability is an architectural constraint from the beginning; the installer product itself is Wave 6. Doctor validates an existing configured profile; it does not create one.
- `docs/architecture/pre-python-gate/configuration-and-installation.md` (bootstrap evidence: a failed signature or wrong profile cannot become ready merely because HTTP responds), `control-plane.md` (health distinguishes live process from ready dependencies; sanitized diagnostics), `hexagonal-contracts.md` (negotiation rejects required unsupported behaviour before launch).

## Binding rules — not delegated

1. Doctor observes and reports. It never repairs, creates or mutates external resources.
2. A check passes only on positive evidence. Reachability is not readiness: an HTTP response, a present config key or a resolvable secret reference is not proof of a working authenticated path.
3. Results are sanitized. No secret, token or raw provider stderr appears in output.
4. Unknown and unavailable are distinct from failed, and each is reported explicitly.
5. **Outcome matrix (Wave 1, fail-closed).** Every check listed in scope is hard-required for autonomous start.
   - **PASS** — the check produced positive authenticated evidence.
   - **FAIL** — autonomous start is refused.
   - **UNAVAILABLE** — a required dependency could not be evidenced; autonomous start is refused, and the result is reported distinctly from FAIL so the operator can tell a broken configuration from an unreachable dependency.
   - **WARNING** — reserved for advisory, non-hard-required checks; it does not block start. Wave 1 defines no advisory checks.
   There is no degraded-autonomy mode in Wave 1, and a profile cannot downgrade a hard-required check to advisory. This follows FD-03 fail-closed semantics. Operator inspection commands remain available while start is refused.
6. Exit codes: `0` all checks PASS; `1` at least one FAIL; `2` no FAIL but at least one UNAVAILABLE; `3` WARNING only. Any nonzero code blocks autonomous start except `3`.
7. Write and publication capability is evidenced by authenticated capability negotiation or a safe non-mutating probe, such as reading back granted permissions. Doctor never performs a product mutation to prove it could.
8. No polling loop is introduced.

## Scope

1. `doctor` application service in `installation/` plus the `control_plane` command wired in PY-08, with per-check results, an overall disposition and machine-readable output.
2. **Checks:**
   - profile configuration loads, is typed-valid, rejects unknown/invalid fields, and names isolated namespaces;
   - secret references resolve to usable handles through the SecretProvider without revealing values;
   - Work Management access: Project reachable, lifecycle Status mapping complete and unambiguous, the `Priority` field present and readable, dependency reading available, and write capability for projections confirmed without performing a product mutation;
   - source-control access: repository reachable, baseline resolvable, candidate publication capability evidenced;
   - provider readiness: worker provider present, version reported, capability and enforceable budget dimensions advertised, authenticated readiness probed;
   - transport health: webhook route/secret configuration valid and signature verification exercised;
   - persistence: store reachable, schema version compatible, migrations settled;
   - execution capability: workspace root writable, Git worktree creation possible, process control available.
3. **Gate integration:** any FAIL or UNAVAILABLE prevents autonomous start and is reported with a sanitized cause and a suggested next action.
4. **Exit codes** per the binding outcome matrix above.

## Non-goals / excluded

`alienintent init`, App creation, repository authorization flows, resumable install steps, rollback (all Wave 6, SF-REQ-037); repair actions; provider benchmarking or routing (Wave 4); dashboards. No Node, FactoryChecks, credential, deployment or product-mutating change.

## Repair cycles (SWF-23)

> **Repairs must converge monotonically unless authority explicitly changes the target.**

Any repair cycle on this BIU carries, alongside this contract:

- **findings to fix** — the specific findings being addressed;
- **previously satisfied acceptance criteria** — criteria already proven in the prior candidate;
- **evidence that must be preserved** — the proof artifacts carrying those criteria;
- **evidence explicitly superseded** — listed item by item, never silently dropped;
- **supersession authority** — the decision or requirement change authorizing it;
- **replacement proof obligations** — what must newly prove the changed target.

Previously verified behavior must remain correct, and previously valid evidence must remain valid or be explicitly superseded. A repair must not fix one defect by regressing another verified property, and must not remove, weaken, bypass or discard proof for a previously satisfied acceptance criterion — tests, negative controls, mutation/proven-red checks, architecture fitness, CI checks, custody evidence, lifecycle proof, dependency proof or operational verification. Evidence disappearance without explicit supersession is a regression and a verification failure. See [SWF-23](../../decisions/2026-09-20-convergent-repair-monotonic-progress.md).

## Acceptance criteria

1. Every check has both a passing and a failing test case, with the failure surfaced as a distinct sanitized result.
2. Negative evidence cases specifically covered: an endpoint that responds but fails signature verification; a resolvable secret reference whose material is rejected by the provider; a Project that is reachable but has an incomplete or ambiguous Status mapping; a missing `Priority` field; an incompatible persistence schema version.
3. A FAIL prevents autonomous start, proven by a real `run` attempt that refuses; an UNAVAILABLE result likewise refuses start and is reported distinctly from FAIL.
4. Doctor performs no external mutation: verified by asserting no write-effect occurs against recorded fixtures and local doubles.
5. Unknown/unavailable is reported distinctly from failed.
6. Exit codes match the binding matrix (0/1/2/3) for each disposition, and JSON output is stable and machine-readable.
7. A profile cannot downgrade a hard-required check to advisory: an attempt is rejected, proven by negative test.
8. A sentinel-secret test proves no secret or token appears in any output.
9. Fitness checks and the Node suite still pass.

## Verification requirements

- Executable proof invoking the real CLI command with real exit statuses retained.
- Live external calls are not required: provider readiness and Work Management checks are verified against recorded fixtures and local doubles; the real-target execution of doctor is evidenced in PY-10.
- Node suite executed and passing.

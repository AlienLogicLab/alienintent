## Intent

Make execution state survive crashes and restarts without duplicating external effects. PY-02 decides what is allowed; PY-03 makes those decisions durable under FD-05 semantics, so that a killed process resumes with one owner per resource and no repeated effect.

## Binding rules — not delegated

1. Operational state is separate from trajectory/evidence state. This BIU builds operational state only; evidence stores are Wave 5.
2. Imported upstream Work Item snapshots are separately identified noncanonical records with provider identity, source version/digest and provenance. They never become canonical product backlog, priority or CAPTURE–READY state.
3. Unknown external effect outcomes block conflicting work. Blind retry is prohibited.
4. Physical exactly-once network delivery is never claimed. Effects are effectively once-only through durable identity, deduplication and idempotency.
5. Profile-scoped keys: N profiles never share unscoped ownership keys.
6. SQLite is the default adapter for this BIU. The port and conformance suite must be written so a PostgreSQL adapter can run the identical cases later without changing the suite.

## Scope

1. **OperationalStore port** in `execution_coordination/ports/` with expected-version commits and typed conflict, unavailable and rejection outcomes.
2. **SQLite adapter** in `execution_coordination/adapters/` using the Python standard library, with profile-scoped keys and explicit transaction boundaries.
3. **Inbox:** durable authenticated-receipt records keyed by event identity, persisted before any acknowledgment of custody, with duplicate delivery returning the prior receipt.
4. **Effect-intent / outbox:** an intent persisted with the domain change in one transaction, an effect execution path carrying the same identity, a confirmed-receipt record, and an explicit unresolved state for unknown outcomes that blocks conflicting mutation until reconciled by read-back.
5. **Reservations** for global, profile and repository scopes: atomic acquisition, owner and fencing token, release, and rejection of release or successor admission by a stale fence.
6. **Recovery/reconcile queries** sufficient for a restarting service to re-establish ownership, pending effects and unresolved outcomes from durable state alone.
7. **Schema versioning** with preflight, fail-closed behaviour on unknown/newer schema, and a migration path that never silently resets state.
8. **Store conformance suite** expressed against the port, parameterised by adapter.

## Acceptance criteria

1. Crash-boundary tests kill the process at each durable boundary — before receipt persistence, after receipt before domain change, after domain change before effect, after effect before receipt-of-effect — and demonstrate on restart: no lost owner, no duplicate effect, and an unknown outcome left explicitly unresolved rather than retried blindly.
2. Duplicate event delivery returns the prior receipt and performs no second domain change.
3. A reordered stale-version write is rejected by the expected-version guard rather than rolling state backward.
4. Two concurrent admissions for one repository scope produce exactly one reservation; the loser receives a typed rejection.
5. A stale fencing token cannot release or supersede a newer invocation's reservation.
6. Profile isolation: identical logical keys in two profiles never collide.
7. Unknown or newer schema version fails closed; a migration runs with preflight and is reversible or explicitly irreversible with evidence.
8. The conformance suite runs entirely against the port, with the SQLite adapter supplied by composition; adding a second adapter would require no suite change.
9. PY-01/PY-02 fitness checks still pass; the Node suite still passes; no vendor or database type appears in a domain or port signature.

## Verification requirements

- Executable proof on a real SQLite file, including real process termination, not simulated exceptions alone.
- Deterministic, repeatable runs with retained output and real exit statuses.
- Node suite executed and passing.

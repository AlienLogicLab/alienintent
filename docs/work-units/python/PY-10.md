## Intent

Demonstrate the Wave 1 product statement on real infrastructure, in one coherent run:

> Given a prioritized backlog, sufficient execution authority, and no unresolved blockers, AlienIntent continuously consumes eligible READY BIUs until the executable backlog is exhausted.

## Architecture references

- **SWF-08 (D-1)** — the proof runs on a dedicated AlienIntent sandbox environment. The Node bootstrap is not stopped, and the two control planes never share a Project/profile in a way that could dispatch the same work.
- **SWF-11** — the acceptance list below is binding and complete.
- **Architecture Authority** §1 deployment topology and profile isolation, §42 Node→Python coexistence, §43 Python Sovereignty (not claimed here).
- `docs/architecture/pre-python-gate/conformance-and-sovereignty.md` — never give both implementations mutation authority over the same profile; mocks alone cannot establish live behaviour; sovereignty requires far more than this proof.

## Binding rules — not delegated

1. **Isolation.** The sandbox repository, its GitHub Project, its Python profile and its GitHub App installation/webhook identity are separate from the live AlienIntent Project and the Node bootstrap's profile. No shared state, workspace root, store or webhook route.
2. The Node bootstrap keeps running and is not modified, paused or reconfigured to enable this proof.
3. This is test/integration infrastructure, not a second product deployment, and not a cutover. No Python Sovereignty claim, no Node retirement, no migration of live work.
4. Sandbox content is deliberately minimal but sufficient to exercise the factory; the backlog BIUs are trivial engineering tasks whose purpose is to exercise the loop.
5. No human moves any individual BIU into IMPLEMENT during the run.
6. Credentials for the sandbox App are referenced through the SecretProvider and never committed; no private installation detail, App ID, hostname or secret appears in the retained evidence.

## Scope

1. **Sandbox environment**: a minimal dedicated repository; its own GitHub Project carrying the same lifecycle Status options plus `Priority`; its own Python profile; its own GitHub App installation and webhook identity/route; minimal source content.
2. **Seeded backlog**: at least three READY BIUs, including at least two of equal priority and at least one dependency, plus one BIU constructed to raise a genuine `HumanDecisionRequired`.
3. **The run**: `doctor`, then `run`, one operator decision submitted through the Decision Inbox, one deliberate process restart mid-run, through to exhaustion of the executable backlog.
4. **Evidence capture**: ordering trace, refill events, reservations, exact candidate revisions and read-back proof, verification results, escalation payload and decision record, restart boundary, projection delivery health and final states.
5. **Written proof report** under `docs/verification/`, with a machine-readable summary, referencing the retained evidence.

## Non-goals / excluded

Running AlienIntent's own backlog on Python; cutover; Node retirement or pause; Python Sovereignty claims (that needs the full S1–S7 matrix); deployment capabilities; performance or cost optimization; Wave 2+ capability. No FactoryChecks change. No Node change except an unrelated §42 critical bootstrap repair, which would be its own BIU.

## Required closure actions

Evaluated under the standing ACCEPT → DONE policy ([SWF-17, SWF-19](../../decisions/2026-09-20-wave1-closure-policy.md)). Closure performs only the minimum remaining actions needed to reach DONE.

- **Landing: required.** A **normal merge commit** of the accepted candidate into `main`, preserving the accepted SHA in `main` ancestry, is **authorized as routine closure** under SWF-19; no separate Founder exception is needed. No rebase, no squash, no rewrite of the accepted SHA, no change to accepted candidate content. If landing would alter accepted content or amounts to a material implementation change, stop and `RETURN_TO_IMPLEMENT`. After landing, run only the required post-merge checks and confirm required CI on the merge result. Merge is a closure operation, not a lifecycle state.
- **Deployment: not required.** No deployable artifact or environment is in scope.
- **Publication/release: not required.** Candidate-branch publication is completed before verification.
- **Live verification: required.** The live proof *is* this BIU's deliverable and is already established by its acceptance evidence; closure records that evidence and performs no new run.
- **BIU-specific: required.** Retain the redacted evidence manifest and publish the written proof report under `docs/verification/`, as scope requires. The sandbox environment is not dismantled by closure.

Closure must not perform opportunistic refactoring, unrelated cleanup, speculative abstraction, unrelated documentation or tests, architecture redesign, additional feature work, or repeated verification already supported by trusted accepted evidence.

**Minimum necessary work (SWF-20 / SF-REQ-048).** At IMPLEMENT, VERIFY, REVIEW, ACCEPT and closure, perform only the work necessary to satisfy this BIU, its lifecycle obligations, applicable architecture/policy and required evidence. Mechanically detectable over-scope work is a verification finding; REVIEW/ACCEPT assesses unnecessary work, unnecessary abstraction, scope expansion and whether a simpler correct implementation was available.

**Closure evidence (SWF-18).** Record what is available without building new telemetry: closure start/end time; actions evaluated, performed and determined unnecessary; tool/command count; changed files; token/cost where reported; authority interruptions; time blocked awaiting human authority; and any `RETURN_TO_IMPLEMENT` occurrence.

## Repair cycles (SWF-23)

> **Repairs must converge monotonically unless authority explicitly changes the target.**

Any repair cycle on this BIU carries, alongside this contract:

- **findings to fix** — the specific findings being addressed;
- **previously satisfied acceptance criteria** — criteria already proven in the prior candidate;
- **evidence that must be preserved** — the proof artifacts carrying those criteria;
- **evidence explicitly superseded** — listed item by item, never silently dropped;
- **supersession authority** — the decision or requirement change authorizing it;
- **replacement proof obligations** — what must newly prove the changed target.

Previously verified behavior must remain correct, and previously valid evidence must remain valid or be explicitly superseded. A repair must not fix one defect by regressing another verified property, and must not remove, weaken, bypass or discard proof for a previously satisfied acceptance criterion — tests, negative controls, mutation/proven-red checks, architecture fitness, CI checks, custody evidence, lifecycle proof, dependency proof or operational verification. Evidence disappearance without explicit supersession is a regression and a verification failure. See [SWF-23](../../decisions/2026-09-20-convergent-repair-monotonic-progress.md).

## Acceptance criteria (SWF-11 — all in one coherent run)

1. At least 3 READY BIUs are consumed.
2. Different priorities are present and respected.
3. At least two equal-priority BIUs prove FIFO ordering.
4. At least one dependency is respected: the dependent starts only after its blocker reaches DONE.
5. WIP = 1 is enforced throughout.
6. Slot refill is automatic on capacity release.
7. One `HumanDecisionRequired` event is emitted with complete context.
8. Only the affected BIU blocks; independent eligible work continues during the block.
9. A durable human decision automatically unblocks and resumes the affected work.
10. A Python process restart occurs during the run.
11. No duplicate execution or duplicate external effect after the restart.
12. Exact candidate custody is proven before every VERIFY.
13. All executable work reaches DONE.
14. No human moves an individual BIU into IMPLEMENT at any point.

Additionally:

15. `doctor` passes against the sandbox before autonomous start, evidenced.
16. The live AlienIntent Project and the Node bootstrap are demonstrably unaffected: no Python-originated event, projection or dispatch touches them.
17. Retained evidence contains no secret, credential, App ID, hostname or private installation detail.

## Verification requirements

- Live executable proof on real infrastructure. Mocks cannot satisfy any acceptance item.
- Independent verification of the retained evidence against the acceptance list by a separate verifier invocation.
- Evidence reproducible and retained with the invocation, including exact revisions and exit statuses.

## Capabilities and budget

Capabilities: sandbox repository workspace, Git, Python toolchain, process control, provider CLI execution, network access to GitHub for the sandbox installation, sandbox GitHub App credentials via SecretProvider. No authority over the live AlienIntent Project, the Node profile, FactoryChecks, or any deployment target.
Budget per SWF-09: hard wall-clock, attempts, retries, concurrency and cancellation; token and monetary cost measured and recorded, never assumed zero. Provider spend is bounded to the minimum needed for the proof.

# PY-01 — Python S0: enforceable architecture skeleton coexisting with Node

**Type:** first canonical Python implementation BIU.

**Baseline:** AlienIntent `f8ddf22`, clean `main`. Node behaviour baseline
`2288cef`, unchanged by this BIU.

**Authority:** Architecture Authority §41 Python repository structure, §39
architecture fitness, §42 Node→Python coexistence; binding FD-02 internal module
decomposition; the Pre-Python gate reclassification of 2026-09-19 recording 0
category C decisions and declaring the architecture decision gate satisfied; EOS
v1.0, whose Adopted Agentic Development Discipline binds this work.

**Conformance:** EOS v1.0 (`DR-000007`). This BIU is subject to the ten Adopted
discipline rules, specifically rule 1 preserve known-good capability, rule 2 one
active vertical, rule 6 executable proof before declaring readiness, and rule 9
monotonic accepted progress from S0.

## Why this is S0

Rule 9 requires accepted capability lineage to start somewhere and for each step to
prove that previously accepted capabilities remain protected. The first thing worth
proving is not domain behaviour but that the architecture is *enforceable*: that
layering violations and vendor-type leakage fail the build rather than relying on
reviewer vigilance. Every later BIU inherits that guarantee.

Rule 6 requires the real intended path through actual components, not mocks. The
real path for this step is: the package structure exists, the fitness checks run
against it, and they genuinely fail when the architecture is violated.

## Outcome

A Python package skeleton under `src/`, organized by the FD-02 approved modules,
with executable architecture fitness checks that enforce the binding constraints,
coexisting with the untouched Node bootstrap in the same repository.

## Scope

1. `src/` layout per Authority §41, with packages for the FD-02 modules: execution
   coordination, invocation runtime, context assembly, evidence and learning, and
   installation, plus control plane as application orchestration.
2. Domain, application, ports, adapters and composition separated as §41 requires.
3. Architecture fitness checks per §39 that fail the build on: a dependency from
   domain or application outward to adapters; a vendor or third-party type appearing
   in a domain or port signature; a port implemented without declaring its contract;
   and configuration read outside the composition boundary.
4. Python packaging, typing and test tooling sufficient to run those checks.
5. Proof that each check fails on a deliberately violating fixture and passes on the
   skeleton, with the failure output retained as evidence.

## Excluded

Domain logic, lifecycle behaviour, persistence, event handling, providers, control
plane operations, installer behaviour and any runtime capability. No Node source,
test, configuration, runtime, service or bootstrap change. No FactoryChecks change.
No credentials, deployment or provider spending. No claim of Python Sovereignty and
no Node retirement.

## Acceptance

1. `src/` exists with the FD-02 modules and the §41 layer separation, and no module
   is promoted to a bounded context.
2. Each named fitness check exists, runs, and is demonstrated to fail on a violating
   fixture and pass on the skeleton. Real failure exit statuses are preserved per
   §39.
3. The Node bootstrap is byte-identical to `2288cef` behaviour: its source, tests
   and configuration are unchanged and its test suite still passes.
4. Python and Node coexist in the one repository per §42, with no shared runtime
   coupling and no Node invocation from Python.
5. Evidence is retained: check output on both the violating fixture and the
   skeleton, and the Node suite result.
6. No category B design work is pre-empted by inventing a contract this BIU does
   not need. Naming a package is not deciding a port signature.
7. Agent-Ready assessed READY before execution; independent review before commit;
   nothing pushed until both pass.

## Known collision to resolve in execution

`src/` is already occupied by the Node bootstrap: `src/config`, `src/domain`,
`src/github`, `src/providers`, `src/runtime`. Authority §41 requires a `src/`
layout for Python and §42 requires the two to coexist in one repository, so the
implementer must choose a non-colliding arrangement that satisfies both.

This is implementation detail under fixed constraints, not an open decision. The
binding constraints are: Node is frozen and must not be moved or modified (§42,
and discipline rule 1); Python uses a `src/` layout organized by the approved FD-02
modules (§41); and neither may invoke the other. Any arrangement meeting those is
acceptable. Record the choice and its rationale in the BIU's evidence so later work
inherits it rather than re-deciding it.

## Relationship to the design backlog

This BIU consumes no unresolved decision. It touches category B rows G06 Python
engineering standard and G32 architecture fitness rules, and completes only the part
of each that S0 requires. Their full acceptance criteria remain in the matrix.

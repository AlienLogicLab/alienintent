## Intent

Prove the continuous factory control loop end to end, deterministically and without provider spend, before any vendor adapter or real worker exists. This is the walking skeleton: from one start command, a prioritized backlog is consumed to exhaustion with no per-BIU human trigger, and a restart mid-run resumes without duplicate work.

## Binding rules — not delegated

1. **No polling.** The loop is driven by events: an upstream-change notification, an internal capacity-release event, or a recorded result. A bounded retry timer is not a backlog poll. A single reconcile snapshot at startup is recovery, not periodic listing.
2. Automatic release defaults ON and is configurable OFF per profile. Both paths cross the same release boundary and guards from PY-02.
3. The loop never invents or reorders product priority.
4. Stop conditions are explicit: eligible backlog exhausted; all remaining work blocked by dependencies or authority; or capacity unavailable. A stop is reported with its reason, never as silent idling.
5. The scripted worker and in-memory Work Management adapter are **test doubles under `tests/`**, not shipped product capability, and must not be presented as SF-REQ-039.
6. **The candidate-custody guard is never bypassed, stubbed, disabled or weakened.** PY-02's guard stays in force for every offline run. The offline candidate is a local-artifact `CandidateRef` satisfying all nine SWF-12 conditions. A scripted outcome that produces no retrievable, digest-verified artifact is refused entry to VERIFY.
7. **A scripted success is an observation, never a verdict.** The offline verifier runs a real deterministic check against the retrieved artifact and emits observations; ACCEPT comes only from policy evaluation over the contract's required evidence.
8. Production custody mechanics — Git worktrees, publication to a retrievable remote, fresh-clone read-back, and a separately invoked verifier process with its own provenance — belong to PY-06 and are **not** built here. PY-04 proves the loop; PY-06 proves production custody.

## Scope

1. **FactoryCoordinator** application service in `execution_coordination/application/`: import READY view → evaluate release policy → admit with reservation → dispatch through the WorkerProvider port → record correlated result → advance lifecycle (IMPLEMENT → VERIFY → REVIEW → ACCEPT → closure → DONE) → release capacity → refill.
2. **Rolling refill** triggered by capacity-release events, selecting the next eligible item by the PY-02 policy.
3. **WorkManagement port** shape: import a noncanonical READY snapshot (work identity, status, priority, dependencies, contract reference/digest, readiness evidence), propose a release, project execution state. No vendor concepts.
4. **WorkerProvider port** shape: invocation + context + grants + budget → start receipt and observable outcomes, with a missing-capability rejection.
5. **Test doubles under `tests/`:** an in-memory Work Management adapter seeded from a fixture backlog, and a deterministic scripted worker whose outcome per invocation is declared by the fixture (success, failure, rework-then-success, timeout, authority block). A scripted success writes an immutable digest-identified artifact to a durable local path outliving its invocation.
6. **Local-artifact custody path:** a candidate store that records the artifact's digest-bearing `CandidateRef`, and an independent retrieval step run in a **separate process** that fetches the artifact, recomputes its digest and proves exact identity before VERIFY is admitted.
7. **Composition wiring** for an offline profile, with the store from PY-03.
8. **Stop-condition reporting** and a structured run summary suitable for later control-plane consumption.

## Candidate custody for the offline proof (SWF-12, approved)

SF-REQ-007 requires that VERIFY is never entered without a durably identifiable and retrievable candidate. PY-04 has no Git worktrees or remote publication, so its candidate is a **durable content-addressed local artifact**. Founder decision SWF-12 approves this as satisfying custody for PY-04. **It is not an exemption.** All nine conditions below are binding:

1. candidate contents are immutable once identified;
2. the candidate has a cryptographic content digest;
3. candidate identity contains or resolves unambiguously to that digest;
4. the artifact persists independently of the PRODUCER invocation;
5. a fresh independent process can retrieve it;
6. the fresh process recomputes the digest and proves exact identity;
7. VERIFY is inadmissible until that independent read-back succeeds;
8. any mutation produces a new candidate identity;
9. candidate/evidence retention follows the normal evidence policy.

Custody is **not semantically tied to Git**. The candidate is represented by the provider-neutral `CandidateRef` from PY-02, whose variants include local artifact, source revision and archive. PY-06 remains responsible for production/source-control custody.

## Required closure actions

Evaluated under the standing ACCEPT → DONE policy ([SWF-17, SWF-19](../../decisions/2026-09-20-wave1-closure-policy.md)). Closure performs only the minimum remaining actions needed to reach DONE.

- **Landing: required.** A **normal merge commit** of the accepted candidate into `main`, preserving the accepted SHA in `main` ancestry, is **authorized as routine closure** under SWF-19; no separate Founder exception is needed. No rebase, no squash, no rewrite of the accepted SHA, no change to accepted candidate content. If landing would alter accepted content or amounts to a material implementation change, stop and `RETURN_TO_IMPLEMENT`. After landing, run only the required post-merge checks and confirm required CI on the merge result. Merge is a closure operation, not a lifecycle state.
- **Deployment: not required.** No deployable artifact or environment is in scope.
- **Publication/release: not required.** Candidate-branch publication is completed before verification.
- **Live verification: not required.** This BIU has no deployed service or live target in scope; the accepted executable evidence and CI are the required proof.
- **BIU-specific:** none.

Closure must not perform opportunistic refactoring, unrelated cleanup, speculative abstraction, unrelated documentation or tests, architecture redesign, additional feature work, or repeated verification already supported by trusted accepted evidence.

**Minimum necessary work (SWF-20 / SF-REQ-048).** At IMPLEMENT, VERIFY, REVIEW, ACCEPT and closure, perform only the work necessary to satisfy this BIU, its lifecycle obligations, applicable architecture/policy and required evidence. Mechanically detectable over-scope work is a verification finding; REVIEW/ACCEPT assesses unnecessary work, unnecessary abstraction, scope expansion and whether a simpler correct implementation was available.

**Closure evidence (SWF-18).** Record what is available without building new telemetry: closure start/end time; actions evaluated, performed and determined unnecessary; tool/command count; changed files; token/cost where reported; authority interruptions; time blocked awaiting human authority; and any `RETURN_TO_IMPLEMENT` occurrence.

## Acceptance criteria

1. From one start, a seeded backlog of at least five BIUs is consumed until exhaustion, with no human action between items and no per-item trigger.
2. Execution order honours declared priority, then FIFO among equal and among absent priority.
3. A dependency-blocked item is skipped while independent eligible work proceeds, and is admitted once its dependency reaches DONE.
4. WIP is respected: with the default of one mutating stream per repository, no second mutating invocation is admitted while one is active; capacity refills automatically on release.
5. A restart in the middle of the run, on the PY-03 SQLite store, resumes with no duplicate dispatch, no lost result and no duplicated effect.
6. Automatic release ON and OFF both produce the same attributable release boundary; with OFF, no execution starts without an explicit release.
7. A scripted rework outcome returns the item to IMPLEMENT and re-verifies before acceptance; a scripted authority block stops only that item and is reported distinctly from a failure.
8. The run terminates with an explicit stop reason when the eligible backlog is exhausted.
9. Custody is enforced, not exempted. Each SWF-12 condition has a test: the artifact is immutable once identified; it carries a cryptographic digest; its identity resolves unambiguously to that digest; it outlives the PRODUCER invocation (proven by retrieval after that process exits); a fresh separate process retrieves it and recomputes the digest to prove exact identity; VERIFY is refused until that read-back succeeds (negative test); mutating the artifact yields a different candidate identity and does not inherit the prior one; retention follows the evidence policy. No test disables or replaces the PY-02 guard.
10. A scripted success alone never yields ACCEPT: acceptance requires policy evaluation over required evidence, proven by a negative test in which the required evidence is absent.
11. No timer drives backlog listing: a test asserts that with no events and no capacity change, the loop performs no repeated Work Management reads beyond the startup reconcile.
12. Fitness checks and the Node suite still pass.

## Verification requirements

- Executable proof of the real loop path with deterministic doubles; no mocked coordinator internals standing in for the loop itself.
- Real process restart during a run, not a simulated restart.
- Retained evidence: run summaries, ordering traces, restart evidence, exit statuses, Node suite result.

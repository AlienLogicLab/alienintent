# Work unit: one identity service, and registration of work items with their definitions

**Label:** `IDENTITY-SERVICE-AND-REGISTRATION` (a document label; the work item's identity is allocated by the service this unit builds, when the item is registered).
**Status:** Draft for independent adversarial review, 2026-10-01 (revision 7.1; revision 7 corrected the two overlapping-writer findings of the independent review of revision 6, and 7.1 removes one duplicated rule that had drifted — section 24). Not approved, not assessed, not released.
**Position on the path:** the first unit of [the shortest dependency path](python-execution-path-20260930.md) (revision 4). Nothing later can read a work record that does not exist.
**Authority:** formal design section 5 (canonical persistence; bounded storage), 6.1 (WorkItem fields), **6.1A** (one identity and a durable history; one identity service; domain rules, application coordination, injected storage), **6.1B**, **6.1C** (splitting preserves origin and obligations; dependencies and cycles), 7.1–7.3 (lifecycle and the CAPTURE preconditions); canonical plan section 2.3; the Founder's decisions of 2026-09-30 (path document section 4).
**Roles:** one PRODUCER (reviews its own complete change before handing it over); one fresh VERIFIER checks the exact published candidate; a REVIEWER performs this adversarial design review; a separate CLOSURE instance lands the accepted candidate. Which model plays which role comes from the shared routing source.

## 0. Why this unit exists (plain English)

Every piece of work must have one permanent name and one permanent record: where it came from, every version of its instructions and every change between them, what was assessed and approved, and — if it was split — its parent and children. Today none of that exists for real work: names are whatever someone typed; the only code that hands out names runs inside the automatic compiler, scoped to one runtime profile, so two profiles could hand out the same name; definitions are Issue text and files on a branch; nothing records lineage.

This unit builds one identity service that every creator of work calls, and a registration operation that records work items with complete, versioned definitions and an explicit family. The work objects enforce the rules; application services only coordinate loading and saving them through injected repositories. A registered hand-written item enters the lifecycle at **CAPTURE** (formal design 7.3: durable authority, explicit priority, no identity conflict); it does not advance to TASKS or READY here, and the existing readiness validation is recorded as information that names what is still missing. Nothing here assesses, approves, or touches GitHub.

Economy: allocation is one read and one compare-and-swap write of one project-wide record; registering a family writes one family record, one row per item, one change record per item, and a fixed small set of evidence objects per item and version (section 7), and re-reads the family record at least once before each member write to prove it still owns the registration; reads cost a fixed, stated number of operations (section 9); nothing scans history; no model runs.

## 2. One observable result

After this unit: (a) every runtime profile of the project obtains identities from one project-wide registry that already contains every name issued or retired before, and the automatic compiler obtains its names through that service without burning names on held compiles; (b) `alienintent work register --family <document>` validates instruction templates, allocates identities, builds and validates the execution objects, records origins, content versions, change records, family links, dependency and obligation checks, and the existing readiness validation's result; items enter at CAPTURE; a registered child may later be named, by identity, as the parent of its own family (a two-level split) without losing its origin; (c) `alienintent work import` records earlier completed work under a new identity with its original label, its verbatim text and contract, and references to its existing history, at DONE, without inventing assessments or approvals; (d) `alienintent work show <identity>` returns a complete, consistent view or a typed reason, in the stated number of reads; (e) repeating any command changes nothing; a conflicting repeat is refused with a named reason; changing instructions A→B→A leaves three change records and two content versions; a crash at any point leaves nothing half-visible and needs no manual reset.

## 5. Domain model (the objects enforce the rules)

| Object | Invariants it enforces |
| --- | --- |
| `ProjectRegistry` (aggregate; one per project) | a name is issued at most once ever; issued and retired names are never recycled; allocation is the existing rule (lowest free number in the family within the width, stable request-key order, collisions and exhaustion reported, never renumbered); a request key maps to exactly one name; a caller's snapshot names are extra occupied names for that call and a snapshot name already issued to a different key is `REGISTRY_INCONSISTENT`; a caller policy different from the recorded one is `POLICY_MISMATCH`; allocation is refused until the registry is seeded; at exhaustion `IDENTITY_EXHAUSTED` — opening a new family or width is a Founder decision, never renumbering; the row holds at most **1,000** entries across `issued` and `retired`: a request whose **new** (not yet issued) names would take it past 1,000 is refused whole as `REGISTRY_ENTRY_LIMIT` (nothing written, every existing entry preserved, a repeat of already-issued keys still succeeds, distinct from `IDENTITY_EXHAUSTED`, which is the number space); because names are never recycled and allocation must see every issued name in one read, entries cannot be archived out of the row — a later storage unit changes the row's representation (for example compacting issued numbers per family) so the limit can rise; until it lands, all registration and compilation for the project stops at 1,000 entries |
| `WorkIdentity` (value) | grammar-valid; issued by the project registry; not constructible by callers |
| `InstructionTemplate` (value) | text non-empty and ≤ 64 KiB; contract fields complete **except** `identity` and `version`; `dependencies` named by member **label** (or an already-registered identity); `budget_policy` complete; baseline 40 hex; requirement ids, obligations, priority well-formed; `template_digest` = digest of these contents |
| `WorkDefinition` (value) | built only from a `WorkIdentity`, an `InstructionTemplate` and a label→identity map; the execution object is the template's contract with `identity` set, `version = template_digest`, and dependency labels resolved to identities, validated by `contract_from_payload`; `text` is stored **verbatim** (no substitution); carries `template_digest`, `text_digest`, `contract_digest`, `version_id = template_digest` |
| `ContentVersion` (evidence) | immutable; identified by `version_id`; holds the definition fields and the refs of the text and contract objects; no predecessor field |
| `ChangeRecord` (evidence) | numbered from 1 per item; `{sequence, from_version_id | null, to_version_id, cause, registration_id}` — **no wall-clock inside** (time lives in the row), so a rewrite after a crash is byte-identical; a change to the current version is refused as a no-op |
| `WorkItem` (aggregate) | formal design 6.1 fields: `identity, kind, title, intent_ref (= origin), priority (P0–P5 or UNPRIORITIZED), state, created_at, updated_at, version (store), authority_ref, acceptance_ref (= current content version ref)`; plus `labels, parent, children, current_version_id, versions: {version_id: ref}, changes: [ref], registrations: {family key: registration_id}, lint: {status, holds}, marks`; state is `CAPTURE` on registration and `DONE` on import; invariants on every mutation: one origin; `versions` and `changes` each ≤ 100 entries (`VERSION_LIMIT` beyond); a child names exactly one parent (its **origin family**, keyed by the parent's identity) and an item may parent at most one family (its **own family**, keyed by its own identity) — two separate records, both links kept on the row; `registrations` holds one stamp per family the row belongs to (≤ 2: origin family and own family); a stamp may be set only by the writer whose registration id is that family's current one, and a write may set the stamp for the family key it writes only if the existing one is absent, the writer's own id, the family snapshot's `previous_registration_id` (the last completed generation), or an id in its `superseded` list — an unknown (newer) stamp refuses the write as `REGISTRATION_SUPERSEDED`; an item's content version is owned by exactly one family — its origin family, or its own family when it has no parent — or, for an imported item, by no family; the **family key** is the parent's identity (`upstream:work-family:<parent identity>`) |
| `WorkFamily` (aggregate) | parent, members (labels → identities), the versions this family owns (`versions`), `parent_version_id` (the parent's exact version at this generation), `registration_id` (digest of the family document's normalized content), `generation`, state `PENDING → COMPLETE`, `superseded: [registration_id]`; obligation assignment: every parent obligation id in exactly one child or in `kept_by_parent` (`OBLIGATION_UNASSIGNED`, `OBLIGATION_DUPLICATED`, `UNKNOWN_OBLIGATION` refused); dependency graph over members and registered items: `MISSING_ENDPOINT` and `CYCLE` refused; membership may grow in a later generation (a further split with a cause) and never shrink, in a supersede as in a generation (`MEMBER_REMOVED`); only the current `registration_id` may complete the family, and every member row it did not write itself is replaced by it before completion; the `PENDING` record carries `pending_member_labels` (the document's member labels) so a supersede can prove the member set did not shrink before any identity exists; a member is a child of at most one family; a child may be the parent of its own **nested family** (keyed by that child's identity): the nested family's parent is named by identity and `version_id` only — no template: the item must be registered (`PARENT_NOT_REGISTERED` otherwise), must not be `DONE` (`PARENT_DONE`), must have a `parent` of its own (a root item named by identity addresses its own family, and may change its version there), and the given `version_id` must equal its `current_version_id` (`PARENT_VERSION_MISMATCH` — a parent's instructions change only through the family that owns its version); the parent's text, contract and obligation ids come from that stored content version, its dependencies are not re-resolved, and its `family_label` is its label; a nested family requires `cause_ref` (the assessment or decision that called for the split); a nested family versions its children only and records the parent's version in `parent_version_id` (a reader tells a nested family from a root one by the parent's identity being absent from `versions`); `superseded` ≤ 20 per generation and cleared when the family completes: a supersede that would exceed it is `SUPERSEDE_LIMIT`, refused, entries preserved, and the pending id can still be resumed |

## 6. Application services (coordination only), repositories, composition

- `WorkIdentityService`: `issued() -> mapping` (read); `create(request_keys, policy, snapshot=None) -> tuple[WorkIdentity, ...]`: load the registry, allocate, save by compare-and-swap; on `VersionConflict` reload and re-allocate, up to 3 times; a key already mapped to a different name is `IDENTITY_COLLISION`; after 3 conflicts `PERSISTENCE_CONFLICT`. `validate(name)` is a read. The **compiler** calls `issued()` and passes the result as `reservations` into `compile_initial` unchanged; when — and only when — a `CompilationCandidate` results, the compiler calls `create` for the keys the candidate assigned that are not yet issued; a held compile issues nothing. `create` may return names other than the candidate's (another process took a name between `issued()` and `create`, and the registry allocates at write time). So, before saving, the compiler compares every issued name with the candidate's assignment; on any difference it **rebuilds** the candidate by calling `compile_initial` again with the post-`create` issued map as `reservations` (a pure function: each key takes its issued name, including every sibling dependency reference), and requires the rebuilt candidate to name exactly the issued names; only that candidate is saved. A candidate whose identities or dependency references differ from the registry is never saved. Names issued in the first pass belong to their keys and are reused, never burned; if the rebuild holds instead, the hold is recorded and the names stay issued for the next compile. The compiler's holds `IDENTITY_GRAMMAR`, `IDENTITY_COLLISION`, `IDENTITY_EXHAUSTED`, `PERSISTENCE_CONFLICT` keep their meanings; `REGISTRY_ENTRY_LIMIT` is surfaced as a further hold, never as a candidate.
- `WorkRegistrationService`: `register_family(document)`, `import_item(document)`, `show(identity, history_page=None)`; loads and saves `WorkItem`, `WorkFamily`, `ContentVersion`, `ChangeRecord` through the ports below; the objects decide validity.
- Ports: `IdentityRegistry` (project scope), `WorkItemRepository`, `WorkFamilyRepository`, `EvidenceRepository` (existing).
- **Where records live:** the registry, item and family records are aggregates in the **project's canonical database** (the same SQLite file the project's operational store uses), under the store's `profile` column set to the project identity — no schema change. Work-item evidence lives in a **project evidence repository** (`LocalEvidenceRepository` opened with project and profile scope both set to the project identity), distinct from per-profile repositories, so refs are valid from every profile.
- **Composition rule:** `composition/work_registry.py` opens the registry, the project database and the project evidence repository from a **project-level** configuration entry (project identity, canonical database path, evidence root). At a profile's first composition it writes `upstream:project-registry = {project, database_path_digest, evidence_root_digest}` into that profile's own store; every later composition of that profile compares and refuses `PROJECT_REGISTRY_MISMATCH` on any difference. This is how a profile pointed at another registry is caught even though it reads the same configuration.
- **Seed:** `work registry seed --document <seed.json>` reads an explicit seed document (the compiler's `identity_snapshot` — `active`, `retired`, `reserved` — and a list of profile names whose `upstream:identity-reservations` records are merged); each source is read by name; `active` and `reserved` names enter `issued` under a `SEED:` key (so a read on them answers `NOT_REGISTERED`) and `retired` names enter `retired`; two sources claiming one name for different keys refuse the whole seed; a seed whose merged names exceed 1,000 entries is refused whole as `REGISTRY_ENTRY_LIMIT`; the registry records `seeded: true` with the seed document's digest; repeating the seed with the same document is a no-op; a different document after seeding is refused.

All evidence records are built deterministically (fixed observer and invocation fields, no wall-clock), so an identical record after a crash is byte-identical and the repository's no-overwrite install (`local_evidence_repository.py` lines 65–67) tolerates it. Per item: 1 origin + per version: text, contract, version, lint (4) + per change: 1 + per family generation: 2.

Not stored here: assessment attempts (next unit; they name a `version_id` and bind `input_sha256` to the digest of the instantiated definition document), approvals, GitHub associations.

## 8. The family document (input format)

JSON, ≤ 256 KiB, paths relative to the document, each referenced file ≤ 64 KiB:

```json
{"schema_version": 1, "project": "<project identity>", "family_label": "QUEUE-CONNECTION",
 "parent": {"label": "QUEUE-CONNECTION", "title": "...", "priority": "P0",
            "origin": {"kind": "requirement" | "decision" | "document", "ref": "<path@revision or URL>"},
            "authority_ref": "<Founder decision or plan reference>",
            "template": {"text_path": "...", "contract_path": "...", "baseline": "<40 hex>",
                         "requirement_ids": [...], "dependencies": [...]},
            "kept_by_parent": ["<obligation id>", ...]},
 "cause_ref": "<review record or assessment attempt ref>",
 "children": [{"label": "IDENTITY-SERVICE-AND-REGISTRATION", "title": "...", "priority": "P0",
               "origin": {...}, "authority_ref": "...",
               "template": {"text_path": "...", "contract_path": "...", "baseline": "<40 hex>",
                            "requirement_ids": [...], "dependencies": ["<member label or identity>"]},
               "obligations": ["<obligation id>", ...]}]}
```

**A nested family** (a registered child splitting further) has a `parent` block of exactly `{"identity": "<registered identity>", "version_id": "<its current version id>", "kept_by_parent": [...]}` — no template, title, priority, origin or authority (any of these present is refused as an invalid document); `family_label` is that item's label; `cause_ref` is required; no identity is allocated for the parent, no origin comparison is made for it, and only the children are new. A root family's parent may also carry `identity` to address its own existing family for a resume, supersede or new generation; its template is then required as usual and its version may change.

**Obligation ids** are derived, not invented: for each clause of the parent contract's `completion_criteria`, `verification_obligations`, `required_evidence` and each of its `satisfied_requirement_ids`, the id is `<field>:` + digest of the exact clause text. The family document lists ids; the registration recomputes them from the parent template and refuses an id that does not exist (`UNKNOWN_OBLIGATION`). Request keys: `LABEL:<project>/<family_label>/<member label>` (the parent's key uses its own label). Labels are permanent; renaming a label is a new item, so the document must not do it.

## 9. Sequences

**`work register --family`**
1. Parse the document; build every `InstructionTemplate` (for a nested family, the parent's definition is the stored content version named by `version_id`); derive obligation ids from the parent's contract; build the `WorkFamily` request and let it check obligations, dependencies (labels resolve to members; identities must be registered items) and cycles. Any refusal names the field; nothing is written. Compute `registration_id`.
2. Load the family record for the parent: by the given `identity` when the parent block names one — the row must exist (`PARENT_NOT_REGISTERED`) and not be `DONE` (`PARENT_DONE`); if the row has a `parent` the family is nested and the given `version_id` must equal the row's `current_version_id` (`PARENT_VERSION_MISMATCH`); if it has none the identity's label key must map to it and the family is its own root family — otherwise by the parent's *label key* (the registry maps the label key to an identity if it exists; otherwise there is no family yet; a parent label already issued as a member label under another family label is `LABEL_IN_USE` — a label names one item, so name it by identity instead; this is a scan of the loaded registry row, not a store read). Decide: no family → proceed; `PENDING` with the same id → resume; `PENDING` with a different id → **supersede**: the document's member labels must be a superset of the record's `pending_member_labels` (`MEMBER_REMOVED` otherwise), and a label not in the completed generation's `members` needs `cause_ref`, as in a new generation; compare-and-swap the family to the new id, keeping `generation` and `previous_registration_id`, replacing `pending_member_labels` and appending the old id to `superseded` (rows still carrying the old id are updated in step 5, and the old writer can no longer write — see step 5); `COMPLETE` with the same id → no-op, return; `COMPLETE` with a different id → **new generation**: the member set must be a superset of the old one (`MEMBER_REMOVED` otherwise) and a further split needs `cause_ref`; set `PENDING` with the new id, `generation + 1`, `previous_registration_id` = the completed id and an empty `superseded`. The `PENDING` write carries only `registration_id`, `previous_registration_id`, `generation`, `state`, `superseded` and `pending_member_labels`; `members`, `versions`, `parent_version_id` and the check refs of the previous generation stay in place until step 6 replaces them. All of this happens **before** any identity is created.
3. `WorkIdentityService.create` for the parent and all children in one call (children only, for a parent named by identity); repeats return the same names; `REGISTRY_ENTRY_LIMIT` refuses the whole call.
4. Build each `WorkDefinition` (identity + template + label map); validate the execution objects.
5. Save the family as `PENDING` if no record exists — a compare-and-swap **create** of an absent record carrying the fields named in step 2; if a record now exists (another writer got there first) nothing is written and the writer reloads it and re-runs step 2. Then for each member: **re-read the family record (1 store read) and stop with `REGISTRATION_SUPERSEDED`, changing nothing further, unless its `registration_id` is this writer's own**; then in one row write each: origin (if new), text, contract, content version (if not in the row's index), lint report, change record `n+1` (unless the version is unchanged), and the row with `current_version_id`, `versions`, `changes`, **`parent`/`children` links and `registrations[<family key>] = registration_id`**, `state` (`CAPTURE` for a new item; unchanged for an existing one), `updated_at`. An existing row with the same origin and the same version gets only its stamp and `updated_at`; a different origin is `IDENTITY_ORIGIN_CONFLICT`. The parent of a nested family receives only its `children` links and stamp: no content version, no change record (its version belongs to its origin family). A row write on behalf of one family changes only the fields that family owns (its link, its stamp and — if it owns the version — the version fields) and carries the other family's link and stamp over unchanged. A row is never written without its links and stamp, so no row can look standalone while its family is pending. The row write itself applies the `WorkItem` stamp rule of section 5 (the single statement of which stamps a writer may replace) and refuses `REGISTRATION_SUPERSEDED` otherwise — a stamp the rule does not admit is a newer registration's, and the family re-read alone cannot exclude a supersede that lands between the re-read and the row write. A superseded writer therefore stops before its first row write, or at the first row the newer writer has reached, and every row it did write carries an id the newer writer is allowed to replace.
6. Save the dependency and obligation check results as evidence; then, in one compare-and-swap (the last write) against the family record as re-read for the last member, set the family's `members`, `versions`, `parent_version_id`, check refs and `state = COMPLETE`; if the compare-and-swap fails, reload the record: `COMPLETE` under this writer's own id (a second resume of the same id finished first) → return as the no-op success; any other id → `REGISTRATION_SUPERSEDED`. Readers compare rows only against a `COMPLETE` record. Return identities, versions, states and lint status.

**Competing registrations** of the same parent are serialized by the family record's compare-and-swap; the loser reloads and re-runs step 2 (it may find the winner completed the same id → no-op). Two writers on one item row are serialized by the row's compare-and-swap; the loser reloads the row and the family and re-applies the rules, stopping if it has been superseded. Every such reload — family create, family compare-and-swap, row compare-and-swap — is bounded to 3 attempts, then `PERSISTENCE_CONFLICT` with nothing further written; this is the "family conflict after 3 retries" of section 13.

**`work import --label <label> --issue <n> --text <file> --contract <file> --baseline <40 hex> --source-ref <ref>…`** (earlier completed work): step 3 with key `IMPORT:<project>/<label>`; origin lists the given source references (Issue URL, packet document path and revision, accepted candidate revision, landing commits, bootstrap assessment record path); the content version is built from the given text (verbatim) and contract (with the new identity set); `lint()` is run and recorded as **information only**; the row is created at `state = DONE` with `marks.imported` and `marks.done`; no assessment attempt or approval is created; a repeat is a no-op. For Issue 153 the inputs are the packet and contract from branch `manual/py-self-00-producer-20260930` at `2f5d3e4` and the references recorded in the path document R1 and R6.

**`work show <identity> [--history k]`** — consistent-read protocol:
1. Read the item row (1 store read). **No row:** read the registry (1 store read) and decide by the name's request key: issued under a `LABEL:` or `IMPORT:` key → `REGISTRATION_INCOMPLETE` naming the identity (the registration rerun writes it); issued under any other key (seeded or compiler-issued, which never have work records in this unit) → `NOT_REGISTERED`; retired → `IDENTITY_RETIRED`; never issued → `UNKNOWN_IDENTITY`. If the row has a `parent`, read its origin family `upstream:work-family:<parent>`; if it has `children`, read its own family `upstream:work-family:<identity>` (1 store read each; a split child that has itself been split reads both).
2. Read the current content version, text and contract (3 evidence fetches).
3. For each family read: it must be `COMPLETE`; read every other member row (≤ 24 store reads) and require, for each member, `registrations[<this family's key>]` equal to the family's `registration_id` **and**, for each member the family versions, `current_version_id` equal to the family's `versions[identity]`; re-read the family (1 store read) and require the same store version as in step 1. Any failure → retry the whole protocol up to 3 times, then `FAMILY_INCONSISTENT` naming the member and which comparison failed; a `PENDING` family → `REGISTRATION_INCOMPLETE`. For a nested family, a parent whose `current_version_id` differs from `parent_version_id` is reported as `PARENT_VERSION_SUPERSEDED` (information: the children were derived from an earlier parent version; re-splitting is later work), not a failure.
4. `--history k`: page *k* of change records through the row's `changes` index: exactly min(20, remaining) evidence fetches, no walking.
Costs asserted in check 11: no family = 1 store read + 3 fetches; one family of *n* members = (n + 2) store reads + 3 fetches; origin family of *n* and own family of *m* = (n + m + 3) store reads + 3 fetches; a missing row = 2 store reads.

## 10. Behavior after each relevant completion

Same document again → no writes. A member's instructions changed → new content version if new (else the existing one from the index), one new change record, row advanced, lint re-run; assessments or approvals naming the old version no longer apply. Changed back to an earlier content → the earlier version reused via the index, a new change record appended. A completed family with a changed document → a new generation (section 9 step 2). A registered child named by identity as the parent of its own family → its origin family, its `parent` link and its version are untouched; its row gains `children` and a second stamp. A design record and proof plan later exist → lint passes on the resulting version; advancing the state is a later operation. Imported, done and cancelled items are marked, never deleted.

## 11. Restart and missed-signal recovery

Crash after step 2 → nothing written or a `PENDING` record that the rerun resumes or supersedes. Crash after step 3 → the same names are returned; until a member's row is written, `show` on its identity is `REGISTRATION_INCOMPLETE` (issued, no row). Crash during step 5 → rows already carrying the current stamp are complete (links included) and, after the family re-read, are rewritten with only their stamp and `updated_at`; a change record written but not indexed is rewritten byte-identically; the rest completes. Crash before step 6 → `show` reports `REGISTRATION_INCOMPLETE` until the rerun completes; while a nested family is `PENDING`, `show` on its parent is `REGISTRATION_INCOMPLETE` even though its origin family is complete — that is intended, not a defect to repair. A `PENDING` family whose document is then edited is superseded, not stuck (up to 20 times per generation). A superseded writer that resumes later — even after the newer registration has completed — stops at its next family re-read or row write with `REGISTRATION_SUPERSEDED`; it changes nothing after that, and any row it wrote before carries an id the newer writer replaces before completing, so the newer family stays consistent whether the old writer crashes or finishes. No manual reset exists or is needed.

## 12. Duplicate-prevention rules

One name per request key project-wide; issued and retired names never recycled; one origin per identity; one content version per content (index); change records contiguous; one `PENDING` per parent, superseding recorded; a member is a child of at most one family and parents at most one; every member row stamped once per family, by the active registration before the family completes; an item's version owned by one family; a label names one item; membership never shrinks.

## 13. Failure behavior

Invalid document, template, obligation id, dependency endpoint or cycle → typed refusal, no write. Unseeded registry, collision, exhaustion, row entry limit (`REGISTRY_ENTRY_LIMIT`), inconsistent snapshot, policy mismatch → refused by the registry, no rows, nothing dropped. Parent not registered, parent done, parent version mismatch, label in use, supersede limit → refused, no write. The four no-row answers of section 9 (`REGISTRATION_INCOMPLETE`, `NOT_REGISTERED`, `IDENTITY_RETIRED`, `UNKNOWN_IDENTITY`) are read answers, not failures. Superseded writer → `REGISTRATION_SUPERSEDED`, stops, no further write; the active writer completes. Origin conflict, member removal, family conflict after 3 retries → refused. Profile pointer mismatch → refused at composition. Store or evidence unavailable → typed error, rerun resumes. Lint holds → recorded, not a failure.

## 19. Acceptance checks (each names the wrong implementation it catches)

1. **One registry per project across profiles.** Two runtime profiles composed over the project entry issue disjoint names and see the same `issued` map; a profile whose own store holds a different `upstream:project-registry` pointer is refused with `PROJECT_REGISTRY_MISMATCH`; an unseeded registry refuses allocation. Catches per-profile registries and a vacuous composition rule.
2. **Seed preserves earlier names.** Seed document with `active` `PY-01`…`PY-08`, `retired` `PY-09`, `reserved` `PY-09B` and one named profile's reservation record holding `PY-10` → none is ever issued again, `PY-11` is next; two sources claiming `PY-10` for different keys refuse the seed; a second seed with a different document is refused; the same document is a no-op. Catches recycling and silent merges.
3. **Compiler through the service without waste.** With the inline reservation and commit removed, the compiler's tests pass; a compile that holds (`INPUT_UNPINNED`, `EXISTING_DECOMPOSITION`) issues no name beyond those already mapped to its keys; a compile that yields a candidate issues exactly its new keys; **the exact race:** `issued()` ends at `PY-10`; the candidate assigns `PY-11` to key K1 and `PY-12` to K2, K1 sorting before K2 in request-key order, with K2 depending on K1; before `create`, the same service issues `PY-11` under a third key for another caller; `create` then returns `PY-12` for K1 and `PY-13` for K2 → the saved candidate names `PY-12` and `PY-13`, K2's dependency reads `PY-12`, no saved record names `PY-11` for K1 or K2, and the next compile reuses both names without calling `create`; **a rebuild that holds:** a registry double that returns for K1 a name the compiler's snapshot lists as `active` makes the rebuild hold (`REGISTRY_INCONSISTENT`) → the hold is recorded, no candidate is saved, K1 and K2 stay mapped in the registry, and the next compile reuses them without `create`; a compiler snapshot naming a registry-issued name under a different key is `REGISTRY_INCONSISTENT`; a different policy is `POLICY_MISMATCH`; a registry at 1,000 entries turns a compile that would issue a name into the hold `REGISTRY_ENTRY_LIMIT` with no candidate recorded and no name issued; the VERIFIER inspects (code review, not a test) that only the registry adapter writes the registry. Catches burning names and a second path.
4. **Children are ordinary identities with explicit links.** Five distinct numbers for a parent and four children; links both ways; nothing generates a letter suffix; `validate` accepts `PY-09B` and rejects `PY-SELF-00`; at exhaustion (a `PY` registry with 99 issued) `IDENTITY_EXHAUSTED`, nothing renumbered.

Catches validating the execution object first.

Catches overwriting, circular history and duplicate storage.

Catches partial exposure, link loss and phantom items.

## Intent

Make missing authority a first-class, non-fatal outcome. When AlienIntent cannot continue without a decision it does not have, it escalates with enough context to decide, blocks only the affected work, keeps independent work running, and resumes automatically once the decision is durably recorded.

## Architecture references

- **Architecture Authority** §36 Operator Control Plane (operator events flow through normal domain interfaces; no state-mutating backdoor), §45 Founder escalation rule (required escalation content), §21 no polling.
- **Binding FD-05** — an unknown external outcome blocks conflicting work rather than causing blind retry.
- **SWF-05** — the software-factory plan is sufficient product authority for this design; no separate architecture record is a prerequisite.
- **Product authority:** plan §Human escalation (escalation fields, Decision Inbox, notification as an adapter concern, no polling, durable authority record that automatically unblocks work), §Planning authority (`HumanDecisionRequired` emitted when authority is missing).
- `docs/architecture/pre-python-gate/control-plane.md` (mutating commands carry actor/authority/expected version/idempotency key), `work-and-release.md` (an authority block stays distinguishable from a failure), `persistence-and-evidence.md` (operational versus evidence stores).

## Binding rules — not delegated

1. An authority block is not a failure. It is recorded, reported and recoverable as a distinct outcome.
2. Escalation happens only when continuing would require authority AlienIntent does not have. It is not a substitute for routine technical decomposition.
3. Blocking is scoped: the affected BIU and its transitive dependents. Independent eligible work continues.
4. A decision is a durable, attributable authority record with actor, authority reference, target BIU version, expected version and idempotency key. It is never a direct state edit.
5. Recording a decision emits a domain event that re-admits affected work through the normal admission guards. There is no separate unblock backdoor.
6. Notification is an adapter concern. No polling.
7. A decision against a superseded BIU version does not silently apply.

## Scope

1. **`HumanDecisionRequired` domain event** carrying the plan's required fields: profile/project, Work Item and BIU version, the exact decision required, why work cannot continue, options, material tradeoffs, recommendation, affected requirements, affected architecture, cost of waiting where material, and what each choice authorizes.
2. **Escalation emission points** in the execution lifecycle and admission path, including the unresolved-effect condition from PY-03 and an explicit worker-raised authority block.
3. **Affected-work computation** over the dependency graph: the blocked BIU plus transitive dependents; its mutating reservation is released while blocked and its workspace retained.
4. **Decision Inbox** application service in `control_plane/application/` over the PY-03 operational store: list open decisions with enough context to decide without reconstructing agent history, show one, and submit a decision.
5. **Durable decision record** and `DecisionRecorded` event that automatically re-admits affected work.
6. **Notification port** with a Work Management projection adapter (an attributable Issue comment via PY-05) as the first notifier, and a no-op notifier for offline profiles.
7. Integration into the PY-04 loop so that escalation never stops the factory as a whole.

## Non-goals / excluded

CLI presentation (PY-08); email/Slack/Telegram notifier adapters; a web surface; assurance-policy escalation levels (Authority §11, later); Requirements ambiguity detection (SF-REQ-012, Wave 2); learning or yield metrics. No Node, FactoryChecks, credential, deployment or provider-spend change.

## Acceptance criteria

1. With three eligible BIUs where one escalates, the escalation is emitted with every required field populated, the other two proceed to DONE, and the factory does not stop.
2. Only the affected BIU and its transitive dependents are blocked; an unrelated dependent of a different BIU is unaffected.
3. The blocked BIU's mutating reservation is released so capacity refills, and its workspace is retained.
4. Recording a decision emits `DecisionRecorded`, re-admits the affected work through normal guards and completes it without restarting the service and without a human moving any item into IMPLEMENT.
5. A duplicate decision submission with the same idempotency key is idempotent; a conflicting payload under the same key is a conflict.
6. A decision naming a superseded BIU version is rejected with a typed outcome and does not unblock.
7. An authority block is reported distinctly from a failure in the run summary and in the store.
8. A decision survives process restart: after restart, the record and its effect remain, and no duplicate unblock occurs.
9. The notifier is an adapter: with the no-op notifier the inbox still functions; with the projection notifier, delivery failure does not change execution state and surfaces as delivery health.
10. No polling is introduced; fitness checks and the Node suite still pass.

## Verification requirements

- Executable proof through the real loop with deterministic doubles, including a real restart around a recorded decision.
- Negative tests for superseded version, duplicate key and conflicting payload.
- Retained evidence: escalation payloads, inbox state, decision records, run summaries, exit statuses, Node suite result.

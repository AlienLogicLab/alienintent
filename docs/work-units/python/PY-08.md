## Intent

Give the operator a first-class way to run, observe, explain, correct and unblock the factory without editing state by hand. This is the minimum operator surface required for the continuous loop to be run and recovered by a human in practice.

## Architecture references

- **Architecture Authority** §36 Operator Control Plane and its critical rule that operator-generated events flow through the same domain/event interfaces and the control plane must not become a direct state-mutating backdoor; §37 human control surfaces (CLI is the minimum required); §33 packaging with a first-class CLI; §35 observability.
- **SWF-04** — installability is an architectural constraint; there is no installer product in Wave 1.
- `docs/architecture/pre-python-gate/control-plane.md` (application model, presentation and observability, ownership-aware operator views), `python-engineering.md` (first-class CLI, structured outcomes, nonzero error status).
- **Product authority:** plan §Human escalation (Decision Inbox as one operator surface), §Priority 0 factory control loop.

## Binding rules — not delegated

1. Every mutating command goes through application services with actor, authority, target, intent, expected version, reason and idempotency key. No command writes the store directly.
2. `explain` is a deterministic account of guards and evidence. No model call, no invented authority.
3. Read output separates upstream provider state, canonical execution state and projection delivery health, labelling each source. An unavailable upstream read does not make valid internal execution state unknown.
4. Both human-readable and machine-readable (JSON) output are supported; failures exit nonzero.
5. Diagnostics are sanitized: no secrets, tokens, keys or raw provider stderr.
6. The CLI is a presentation adapter in `control_plane/adapters/` over application services; a later web surface would reuse the same services.
7. Operator priority or product-ownership changes belong upstream in the Work Management Provider, not in a local backlog.

## Scope

The **P0 minimum** command set:

1. `run` — start the service/loop for a profile; refuses to start autonomous work when `doctor` fails (the check itself is PY-09; this BIU provides the gate and the entry point).
2. `stop` — stop safely, quiescing owned work.
3. `status` — active/queued/blocked work, capacity and WIP, current lifecycle state per BIU, last events, projection delivery health.
4. `explain <biu>` — the deterministic guard and evidence account of why the item is or is not progressing.
5. `cancel <target>` — enter the PY-06 cancellation protocol with actor and reason.
6. `reconcile` / `resume` — re-establish the upstream view or repair a downstream projection from the current execution revision; resume recovery after restart.
7. `decisions list | show <id> | decide <id>` — the PY-07 Decision Inbox surface, submitting a durable attributable decision.
8. `version` — version and install diagnostics.
9. Structured logging and health/readiness output distinguishing live process from ready dependencies.

## Non-goals / excluded

Replay and synthetic-event emission; inspection of cost, routing, grants and adapter health beyond what `status` already shows; a web interface; configuration editing commands; `alienintent init` (SWF-04); dashboards (SF-REQ-036, Wave 6). These remain the SF-REQ-034 P5 polish scope. No Node, FactoryChecks, credential, deployment or provider-spend change.

## Acceptance criteria

1. Each command runs against a real PY-04/PY-06/PY-07 profile and produces both human and JSON output, with nonzero exit on error.
2. A mutating command without valid actor/authority is denied; a stale expected version is rejected; a repeated command with the same idempotency key is idempotent.
3. No command can transition state except through normal domain guards: a negative test proves the CLI cannot force an invalid transition or write the store directly.
4. `explain` output reproduces the exact guard outcomes the kernel applied, verified against the kernel's own decision for the same input.
5. `status` labels upstream, execution and projection sources separately; with the upstream provider unavailable, execution state is still reported as known and the upstream section is explicitly unavailable.
6. `cancel` enters the PY-06 protocol and preserves evidence; `reconcile` never imports an external ACCEPT/DONE as execution truth.
7. `decisions decide` records a durable decision that unblocks affected work, with no direct state mutation.
8. `run` refuses to begin autonomous work when the readiness gate fails.
9. Sanitization: a sentinel-secret test proves no secret reaches any output stream.
10. Fitness checks and the Node suite still pass.

## Verification requirements

- Executable proof invoking the real CLI as a subprocess, not by calling internal functions only, with real exit statuses retained.
- Negative tests for authorization, staleness and backdoor mutation.
- Node suite executed and passing.

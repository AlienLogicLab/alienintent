# Work unit: assess the exact instructions of a registered work item

**Status:** Draft for independent review, 2026-10-02 (revision 3). Not approved, not assessed, not released.
**Origin:** row 2 of [the shortest dependency path](python-execution-path-20260930.md), narrowed (section 1). Builds on the landed units [`identity-service-and-compiler-connection.md`](identity-service-and-compiler-connection.md) (`main` `73341e3`) and [`work-registration-and-family-history.md`](work-registration-and-family-history.md) (`main` `033006f`).
**Roles:** one PRODUCER (reviews its own complete change before handing it over); one fresh VERIFIER checks the exact candidate; a REVIEWER performs the independent design review; a separate CLOSURE owner lands the accepted candidate.

## 0. The whole design (plain English)

A registered work item already points at its instructions: a packet file at an exact Git commit. This unit adds one operation, `work assess <id or label>`. It reads those exact bytes, runs Agent Ready on them through the existing assessment connection, keeps the attempt and Agent Ready's own output in the existing retained-assessment store, and saves a reference to that output on the work item. A later reader goes from the work item to the output in one step and can check that it was produced from exactly the instructions the item points at. Repeating the command reuses a completed assessment of the same instructions instead of running Agent Ready again; a run that produced no usable result (a failure, or an interruption the operator names) is run again. A new version of the packet file at the same path is assessed as a new revision: the item's pointer moves to the new commit while the item is at `CAPTURE`. The assessment is a record only: it does not make the work READY, approve it, or change its state.

**Why it matters:** today every packet is assessed by hand in a separate terminal and its result copied into a private folder. Nothing ties that result to the work item, a later reader must rebuild the context, and nothing stops a second run or an assessment of the wrong text.

## 1. Narrowed from the path row

Row 2 also asks to create a design record and proof plan "from hand-authored inputs so the validation passes". Checked on `main` `033006f`, this cannot fit one unit: the existing design record (`DesignContract`, `context_assembly/domain/design_admission.py`) must name requirement revisions and is only current against the requirements inventory (`composition/upstream_integration.py` `current_vector`), and a proof plan is derived per requirement from a `RequirementRevision` and its mappings (`evidence_learning/application/proof_planning_service.py` `derive`). ## 4. Rules (domain: `context_assembly/domain/packet_assessment.py`)

- **Fingerprint:** `digest(canonical({"kind": "registered-packet", "id": <row id>, "repo", "path", "commit"}))`. The `kind` field keeps it distinct from any fingerprint `ReadinessAdmission` computes.
- **Identity in the assessment store:** the row's `id`.
- **Text sent to Agent Ready:** the packet bytes decoded as UTF-8, exactly; `input_sha256` is `digest` of that text.
- **Reuse:** if the latest attempt for the id has this fingerprint and a recorded outcome that is not a failure, it is the result; Agent Ready is not run.
- **Run:** otherwise (no attempt, a different fingerprint, or the latest failed), open a new attempt with the latest as predecessor and run Agent Ready once.
- **Recover:** if the item has an attempt with this fingerprint and no outcome (found in `consumer.history(id)`, not assumed to be the latest), a plain call returns `ATTEMPT_IN_PROGRESS` with that attempt's id and launches nothing. `recover=<that attempt id>` first requires **confirmed exit**, using the existing worker-runtime `ProcessOwnership` (`invocation_runtime/adapters/process_ownership.py`): before launching, the service records the running `work assess` process with `consumer.annotate(id, attempt, "owner", ownership.current())` (if that cannot be recorded, nothing is launched), and Agent Ready is started with the existing markers `ALIENINTENT_INVOCATION_ID=<attempt id>` and `ALIENINTENT_INVOCATION_OWNER` in its environment. If no owner is recorded yet, recovery first writes its own `ownership.current()` to the same write-once `annotate(id, attempt, "owner", …)`, so an original that was paused before recording its owner then gets `ATTEMPT_CONFLICT` and launches nothing; if that write conflicts, the owner already recorded is checked instead. Recovery proceeds only if the recorded owner is recovery itself or `ownership.owner_state(owner)` is `terminated`, **and** `ownership.owned_work(attempt id)` is empty; otherwise — including `unknown` or an unreadable `/proc` — it is refused with `ASSESSMENT_PROCESS_RUNNING`, listing the process ids, and nothing changes. Stated limit: Agent Ready gives its provider a filtered environment, so the provider does not carry the marker; it can outlive the check only if Agent Ready itself was killed from outside, because the existing producer kills Agent Ready's whole process group on timeout and on any error. Only then does recovery record that attempt as failed with the existing `consumer.observe(None, AttemptMetadata(id, attempt, fingerprint, input_sha256, exit_status=None, timed_out=False, custody=None, binding), "interrupted:operator")` — the same form `ReadinessAdmission` uses for a raising adapter (`"raised:<error>"`), so the label is kept in the recorded outcome — then runs as above. A `recover` id that is not the in-progress attempt for this fingerprint is refused with nothing changed. `--recover` cannot be combined with `--file`/`--commit`. If recording the failure returns a `Hold` (the run finished first), recovery stops, returns it and launches nothing. If the interrupted run delivers a result after recovery, the store refuses it as `ATTEMPT_CONFLICT`; nothing is overwritten. Because exit is confirmed first, a replacement never starts while the original `work assess` or Agent Ready still runs.

## 5. Sequence and components

`work assess <id or label> [--file <packet.md> --commit <40 hex>] [--recover <attempt id>]` (`--file` and `--commit` only together, and never with `--recover`) → `PacketAssessment.assess(id_or_label, revision, recover)`; with no assessment configured the CLI returns `readiness-not-configured` and nothing else runs:
1. `show(id_or_label)`. Unknown → `UNKNOWN_IDENTITY`. A `request_ref` that is not `packet:…` (an imported `issue:` item keeps its imported evidence; a compiler `requirement:` item is assessed by `ReadinessAdmission` in its own store) → `NOT_A_REGISTERED_PACKET`; retired → `IDENTITY_RETIRED`; without a revision, instructions that are not UTF-8 → `INSTRUCTIONS_NOT_TEXT` (with a revision, step 2a checks the new file instead). Nothing is opened on any of these. They and the holds below are returned as answers, the way `work show` returns `UNKNOWN_IDENTITY`; the CLI's error codes do not change.
2. `binding_refusal(binding)`: a refusal is retained with `consumer.retain` and returned as `CAPABILITY_PROVENANCE_HOLD`, as `ReadinessAdmission` does; nothing is launched and no pointer moves.
2a. Only now, if a revision is given: the file's bytes must be UTF-8 (else `INSTRUCTIONS_NOT_TEXT`); `WorkIdentityService.set_pointer` with the row's repository and path, that commit and those bytes (its refusals are returned unchanged and nothing is assessed); then `show` again, so the steps below use the moved pointer.
3. Reuse or run (section 4). A run opens the attempt (persisted before launch; `contract_digest` and `lint_ref` are `None`), runs the producer through the shared method, and records the response with `consumer.observe`. A `Hold` from opening or recording is returned unchanged and nothing is saved on the item; `ATTEMPT_IN_PROGRESS` is returned with the id of the in-progress attempt for this fingerprint (section 4).
4. On a recorded disposition (READY, CLARIFY, SPLIT or HOLD, retained verbatim): if the fingerprint of the row read again with `show(id)` after recording still equals the attempt's `input_fingerprint` (the pointer has not moved since the run began), `consumer.raw(id, attempt)` and `set_evidence(id, "assessment", ref_from_document(<that raw reference>))`; otherwise the attempt stays retained and the reference is not saved. On reuse the same `set_evidence` is applied, so a crash between recording and saving the reference is repaired by the next call. On a failure: nothing is saved on the row; the result names the attempt and failure class.

**Components.** Domain rules: `context_assembly/domain/packet_assessment.py`. Service: `context_assembly/application/packet_assessment.py` (Work Preparation), given `WorkRecordService`, `WorkIdentityService`, the `AssessmentConsumer` port, the binding, the ownership object, and a per-attempt producer builder `(attempt_id, owner) -> ReadinessAssessment`. **Composition** (`composition/work_registry.py`): the project configuration entry gains one optional object, `"readiness": {"database", "evidence_root", "executable", "provider"}`, read by the existing `project_configuration` (missing → no assessment service; malformed, or a `database` equal to the work database or any configured profile database → `ConfigurationInvalid`). When present, composition builds `SQLiteOperationalStore(database)`, `LocalEvidenceRepository(evidence_root, project, "work-preparation")`, the consumer (`RetainedAssessmentConsumer(repository, store, project, "work-preparation", definition_ref, "alienintent work assess", frozenset({"public", "private"}))`, with `definition_ref` built from the consumer module's bytes the way `composition/evidence_profile.py` lines 28–30 build theirs), the binding (`resolve_binding(executable, "cli")`) and the per-attempt builder `lambda attempt, owner: compose_producer(binding, provider, {**assessment_environment(), INVOCATION_MARKER: attempt, INVOCATION_OWNER_MARKER: owner_token(owner)})`, and exposes `WorkRegistry.assessment`. **CLI:** `work assess <id or label> [--file <packet.md> --commit <40 hex>] [--recover <attempt id>]`, `--file` and `--commit` only together and never with `--recover`; no profile assessment → `{"error": "readiness-not-configured"}`.

## 6. Tying the assessment to the exact instructions

The attempt's opened record holds the fingerprint (id, repo, path, commit) and `input_sha256` of the text sent. The row's `assessment_ref` names the raw output `readiness/<id>/<attempt>/raw`. A reader: row → `assessment_ref` → the entry of that one item's attempt list (`consumer.history(id)`, never all items) whose `raw_ref` equals it → fingerprint and `input_sha256`, compared with the row's pointer and `git show` of it.

## 7. Repetition, interruption, changed instructions, failure

- **Repeat:** reuse (section 4); no second Agent Ready run; the reference is (re)applied.
- **Interrupted** (attempt opened, no outcome recorded — for example the terminal was closed): a plain rerun returns `ATTEMPT_IN_PROGRESS` with the attempt id and launches nothing, so plain reruns never overlap; `--recover <that id>` records it as failed and runs again (section 4).
- **Changed instructions:** the item stays the same (its `request_ref` is repository and path); `work assess --file --commit` moves its pointer to the new commit while it is at `CAPTURE`, after the bytes and retained-commit checks, and publishes the moved tag. The new fingerprint makes it a new assessment; earlier attempts stay retained; `assessment_ref` names the newest. Past `CAPTURE` the pointer cannot move (`POINTER_PRESENT`), so approved instructions cannot change under an approval.
- **Agent Ready fails** (raises, times out, malformed output): the shared method turns it into a failed response and `consumer.observe` records an attempt failure; the row is unchanged; a rerun runs once more with the failed attempt as predecessor.

## 8. Temporary resources

The CLI producer adapter creates and removes its own temporary directory per run (`agent_ready_producer.py`, `TemporaryDirectory`). This unit creates none.

## 9. Permissions and prohibited actions

Prohibited: calling `consumer.consume`, `set_state`, release or approval records; routing CLARIFY questions or SPLIT handoffs; reading the working tree or a branch head for the instructions; storing packet text in the work database; a second assessment store or any cache of results; changing the identity, registration or publishing code beyond the permitted files; GitHub reads or writes; `subprocess`, `uuid`, `datetime` or `time` in domain or application code.

## 11. Acceptance checks (each names the wrong implementation it catches)

Run with a fixture producer except check 7.

1. **Exact instructions.** Assessing a registered row stores one attempt whose fingerprint is section 4's for the row's pointer and whose `input_sha256` is the digest of `git show <commit>:<path>`; the text the producer received is byte-equal to it even when the working tree and the branch head hold a different version; `assessment_ref` names that attempt's raw output and `consumer.raw` returns the producer's output unchanged. Catches assessing the working tree, a branch head or a rebuilt text, and an unretrievable result.
2. **Repeat and crash.** A second call runs the producer zero times and returns the same attempt; with a fault injected after the outcome is recorded and before the reference is saved, the rerun saves it without running the producer. Catches duplicate runs and a lost reference.
3. **Failure, provenance and interruption.** A producer that raises or times out leaves a recorded failure and an unchanged row, and the rerun runs once with that attempt as predecessor; an unestablished binding returns `CAPABILITY_PROVENANCE_HOLD` with nothing launched; an attempt opened without an outcome makes a plain rerun return `ATTEMPT_IN_PROGRESS` naming it, with nothing launched; `--recover` with that id is refused with `ASSESSMENT_PROCESS_RUNNING` while the recorded owner process is alive or a fixture process carrying the attempt's marker is alive, and after both have ended records the attempt failed and runs once with it as predecessor; an original paused before recording its owner launches nothing after recovery; `--recover` with any other id, or after an outcome, changes nothing; a late result for the recovered attempt is `ATTEMPT_CONFLICT`. Catches lost failures, launches without provenance, double launches and an item blocked for good.
4. **New revision.** After a new commit changes the packet at the same path, `work assess --file --commit` on a `CAPTURE` item moves the pointer, publishes `work/<id>` at the new commit to the local bare remote, and runs a new assessment whose fingerprint and `input_sha256` match the new commit; the earlier attempt stays retained; a file that differs from Git at that commit is `POINTER_MISMATCH` with nothing assessed; past `CAPTURE` it is `POINTER_PRESENT`; on a compiler `requirement:` item, an imported item, a retired item, with no assessment configured, or with a refused binding, the pointer and the remote tag do not move; an old run finishing after the pointer moved does not have its reference saved. Catches a stale assessment of changed instructions and a pointer moved without its checks or tag.
5. **Not an approval.** After a READY disposition the row's state is unchanged and a recording wrapper shows no `consume`, `set_state` or release call. Catches an assessment treated as approval or eligibility.
6. **Refusals and wiring.** Unknown id, an imported `issue:` item (its evidence unchanged), a compiler `requirement:` item, a retired row and non-UTF-8 instructions each refuse with nothing opened; a `readiness.database` equal to a profile database is `ConfigurationInvalid`; `work assess` through `work_registry_profile` with and without the `readiness` entry; `ReadinessAdmission`'s existing tests pass unchanged and the FX-U9 controls K34, K46, K47 still match; the test files named in section 10 and `check_architecture.py --check all` pass.
7. **Real use, before acceptance (the VERIFIER inspects, the Founder runs).** Before release, the release owner lands this packet byte-identical to its READY revision on `main` as one docs-only commit (as for the earlier units) and writes a project configuration file, outside the repository, whose work database, `readiness` store and evidence folder are all new, under `~/.local/state/alienintent/manual/assess-real-use/`, so the not-yet-accepted candidate touches no existing database. With this packet registered from that `main` commit with `work register`, the Founder runs `work assess` on it in a separate terminal (the Agent Ready claude provider cannot run inside a Claude Code session). The VERIFIER checks: the row's `assessment_ref`; the attempt's fingerprint and `input_sha256` against `git show` of the row's pointer; the digest of the saved raw output equal to the attempt's recorded `raw_digest` and its disposition equal to the recorded outcome; the row's state unchanged; a second `work assess` running nothing. The run uses the candidate's code (from the VERIFIER's checkout of the exact candidate); the VERIFIER may ACCEPT only after inspecting this evidence, so CLOSURE lands only a candidate proved in real use.

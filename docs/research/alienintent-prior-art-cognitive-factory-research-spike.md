# AlienIntent Prior-Art Research Spike — Software Factory + Project Cognitive Intelligence

**Date:** 2026-09-20  
**Status:** Research-backed strategic record  
**Purpose:** Establish what already exists before canonizing AlienIntent's "software factory + project cognitive intelligence factory" thesis.  
**Novelty posture:** **Do not claim novelty at the category level.** The broad idea already exists in multiple forms. AlienIntent differentiation, if any, must be stated more precisely.

---

## 1. Executive conclusion

The deeper research materially changes the preliminary framing.

The broad concept:

> **software factory + persistent project knowledge/memory + agent specialization + continuous improvement**

is **not novel**.

Several current systems already implement substantial portions of it.

The closest direct overlap found is **8090 Software Factory**. It already presents an AI-native SDLC with:

- project Requirements;
- technical Blueprints;
- Work Orders;
- a project Knowledge Base;
- project skills;
- institutional-knowledge preservation;
- agent-assisted decomposition;
- drift detection between requirements, architecture, work, and code;
- a unified agent spanning modules;
- MCP integration with external coding agents.

**OpenVibely** is also very close from the execution/orchestration direction. It already combines:

- persistent project context/history;
- project memory;
- reusable skills;
- autonomous SDLC loops;
- multi-provider agents;
- long-running goals;
- schedules/task chains;
- isolated worktrees;
- review workflows;
- proactive alerts;
- memory and skill curation.

Therefore AlienIntent should **not** position itself as the first product to combine software generation with durable project intelligence.

The potential differentiation is narrower and more architectural:

> **AlienIntent can become a provider-neutral, evidence-driven software factory in which the project's cognition, authority, verification evidence, engineering trajectory, and specialization mechanisms are explicit first-class assets owned by the project rather than a model vendor or transient agent session.**

That remains a meaningful thesis, but it must be demonstrated rather than assumed.

## 2. Most important finding: 8090 Software Factory is very close

8090 is not merely a backlog plus coding agents.

Its current public documentation describes a coordinated environment in which product intent, architecture, implementation work, context, skills, and code remain linked.

### Requirements

8090 treats Requirements as authoritative product-intent artifacts. Its Requirements Agent can:

- draft requirements from notes, transcripts, designs, images, and code;
- detect ambiguity, gaps, conflicts, and duplication;
- propose feature splitting/merging/reorganization;
- maintain alignment with technical Blueprints;
- require user confirmation for structural changes.

This is very close to AlienIntent's proposed Requirements IR / Director-assisted planning boundary.

### Blueprints

8090 Blueprints are technical specifications defining how requirements are implemented.

The Blueprint agent has context across:

- Blueprints;
- codebase index;
- Knowledge Base;
- Requirements;
- Work Orders;
- linked code and recent code changes.

8090 continuously checks for drift among:

- requirements;
- blueprints;
- code.

Alerts are evidence to investigate, not automatic instructions to change the system.

This overlaps strongly with AlienIntent's architecture-conformance and drift-prevention goals.

### Work Orders

8090 Work Orders are bounded execution artifacts grounded in Requirements and Blueprints.

They contain:

- ID/status/phase;
- purpose;
- acceptance criteria;
- out-of-scope boundaries;
- links to upstream Requirements and Blueprints;
- optional implementation plan;
- activity history;
- E2E acceptance-test descriptions.

Their writing guidance explicitly says a Work Order is an execution boundary and should eliminate ambiguity and prevent scope drift.

This is extremely close to the conceptual role of the AlienIntent BIU.

### Knowledge Base

8090's project Knowledge Base stores context that drives its assembly line.

It supports:

- uploaded project artifacts;
- meeting transcripts;
- product research;
- release notes;
- ongoing decisions;
- automation that collects/organizes/updates knowledge;
- agent-assisted reorganization.

This is already a form of persistent project cognition, though public documentation presents it primarily as contextual knowledge rather than a typed epistemic/authority model.

### Skills

8090 explicitly stores reusable project skills as durable, versioned shared knowledge.

Skills can be:

- general;
- Requirements-specific;
- Blueprint-specific;
- Work-Order-specific;
- Knowledge-Base-specific.

Built-in writing-rule skills are automatically loaded and versioned.

This is strong evidence that the "project learns reusable agent behavior" concept is already commercial product functionality.

### Unified Agent

As of 8090's 2026 changelog, its unified agent operates across the whole assembly line rather than separate module agents, retaining conversation history across requirements, blueprints, and work orders.

This is especially relevant to AlienIntent's proposed Director/Coordinator role.

### Important distinction still visible

8090 appears strongly **human-collaborative**:

- user confirmation for structural requirement changes;
- human review of drift alerts;
- external coding agents pull Work Orders and mark them In Review;
- agent suggestions remain reviewable.

AlienIntent's target is more autonomous in execution:

> authorized requirements + priority + authority → factory continuously executes until exhausted, blocked, or a genuine authority decision is required.

That autonomy/authority split may remain a differentiator.

## 3. OpenVibely is very close on persistent autonomous engineering operations

OpenVibely describes itself as a software factory for running coding agents at scale across projects.

Its overlap includes:

- project code/context/history/memory/agents/workflows kept separately per project;
- autonomous SDLC routines that inspect for product gaps, bugs, performance opportunities, and redundant code;
- proposed work awaiting approval;
- parallel task execution;
- long-running goals/schedules/task chains;
- reusable agent profiles;
- memory curation;
- skill curation;
- multi-provider operation;
- project-aware chat;
- external channels;
- isolated Git worktrees;
- live state, logs, changed files, review comments, alerts, insights.

Two features are especially relevant:

### Memory curation

OpenVibely explicitly says it can autonomously create, recall, update, and consolidate durable project memory so repeated context does not need to be re-explained.

### Skill curation

It also explicitly says it can learn from completed work and improve reusable standalone or agent-owned skills.

That means AlienIntent's "execution → accumulated knowledge → skills" flywheel is not unique as a concept.

What remains potentially distinctive is the governance model:

- typed authoritative objects;
- explicit evidence provenance;
- separation of definition/observation/verdict;
- deterministic authority kernel;
- project-owned cognition independent of provider identity;
- specialization promoted from measured factory yield rather than general memory curation alone.

These differences require implementation evidence, not rhetoric.

## 4. Software Factory Foundation confirms the category is forming

The Software Factory Foundation publicly defines a software factory as a structured multi-agent system that plans, writes, reviews, tests, and deploys software through coordinated loops.

Its stated common architectural patterns include:

- explicit roles;
- persistent memory;
- structured handoffs;
- machine-readable policy;
- human-in-the-loop review;
- continuous self-improvement;
- machine-readable architecture;
- verifiable deployment.

This is strong evidence that "software factory" is becoming an established category rather than an AlienIntent-specific framing.

AlienIntent should therefore avoid category novelty claims and instead specify its operating model precisely.

## 5. Compound Engineering validates the knowledge-compounding loop

Every's Compound Engineering plugin explicitly describes the goal:

> each unit of engineering work should make the next one easier.

Its loop is:

- brainstorm;
- plan;
- work;
- review;
- compound.

The `compound` step records learning into durable project artifacts that future brainstorms/plans read as grounding.

It also supports organization-level rule packs.

This validates a core AlienIntent direction:

> useful engineering knowledge should survive the agent session and improve later work.

However, Compound Engineering mainly expresses cognition as:

- documents;
- prompts;
- skills;
- rule packs.

AlienIntent's potential extension is to make project cognition a broader structured domain including authority, evidence, trajectories, provider outcomes, requirements, decisions, and specialization.

## 6. Memory substrates already exist

### MemoryGraph

MemoryGraph provides persistent graph memory for coding agents with relationship tracking and recall across sessions.

It demonstrates that:

- project memory;
- graph relationships;
- agent recall;
- cross-session persistence

are already commodity-ish infrastructure.

### Engram

Engram describes itself as an epistemic memory substrate for agents.

It provides:

- structured provenance-tracked knowledge graph;
- session continuity;
- contradiction/retraction handling;
- self-maintenance/consolidation;
- identity continuity;
- visualization.

This is even closer to the epistemic side of the Project Cognition concept.

### Consequence for AlienIntent

AlienIntent should **not assume it should build a low-level memory database from scratch**.

The deeper architectural question is:

> What is AlienIntent's Project Cognition domain model and governance contract, and which storage/retrieval substrate best implements it?

Memory storage is infrastructure.

Cognitive authority, evidence semantics, promotion, retrieval policy, and factory integration are the higher-value AlienIntent concerns.

## 7. Academic research strongly supports the cognitive flywheel

### Self-Evolving Coding Agents survey

The 2026 survey "Self-Evolving Coding Agents" explicitly defines evolution across:

- framework;
- memory;
- skills;
- tools;
- models;
- collaboration structures.

It identifies:

- executable feedback;
- repository context;
- coding trajectories

as natural substrates for agent self-evolution.

It also warns about:

- feedback reliability;
- benchmark overfitting;
- safety;
- maintainability;
- cost;
- generalization.

This maps almost directly to AlienIntent's proposed Engineering Trajectory → Quality Evidence → cognitive improvement loop.

### Socratic-SWE

Socratic-SWE demonstrates a concrete closed-loop mechanism:

- collect historical solving traces;
- distill recurring failures and effective repair patterns into structured skills;
- use those skills to generate targeted future tasks;
- validate through execution;
- repeat.

This is strong prior art for:

> trajectories → reusable skills → better future agent performance.

AlienIntent therefore should not claim originality for this mechanism.

Its potential contribution would be integrating it into a broader governed project cognition and software-factory architecture.

### Self-Evolving Software Agents

Additional research describes agents capable of evolving goals, reasoning, and executable behavior in response to experience.

This reinforces that autonomous cognitive evolution is already an active research area.

## 10. Candidate AlienIntent differentiation

The following combination still appears meaningfully differentiated in this research, though it requires further validation and implementation evidence.

### 10.1 Project-owned cognitive sovereignty

> Model providers supply replaceable reasoning capacity; the project owns its cognition.

This means project continuity does not depend on:
- one model;
- one vendor;
- one chat;
- one agent identity.

### 10.2 Typed authoritative cognition

Project truth is represented as bounded domain objects rather than generic "memory".

Potential examples:

- Requirement;
- Decision;
- ArchitectureRule;
- BIU;
- Candidate;
- Observation;
- Verdict;
- EngineeringTrajectory;
- QualityEvidence;
- HumanDecision;
- ProviderCapability.

This is stronger than a document Knowledge Base if fully implemented.

### 10.3 Explicit authority model

A reasoning model can propose but does not acquire authority by reasoning.

Founder/product/architecture/policy authority remains explicit and mechanically enforceable.

### 10.4 Definition ≠ Observation ≠ Verdict

This creates a rigorous epistemic separation between:
- what must be true;
- what was observed;
- what conclusion is authorized.

This appears less common in commercial factory products.

### 10.5 Deterministic kernel + broad Director intelligence

Director intelligence handles:
- interpretation;
- planning;
- decomposition;
- diagnosis;
- recovery proposals.

The deterministic kernel owns:
- state;
- lifecycle;
- budgets;
- capabilities;
- candidate custody;
- verification admissibility;
- effect execution.

This separation is central.

### 10.6 Factory-yield-driven specialization

Skills/tools/specialists should not simply accumulate.

AlienIntent's intended rule is:

> specialize because measured project/factory evidence demonstrates material benefit.

Relevant measures include:
- first-pass acceptance;
- rework;
- architecture violations;
- drift;
- escaped defects;
- cost;
- latency;
- context efficiency.

### 10.7 Dual factory output

The strategic output is:

1. verified software;
2. project-owned cognitive capability for continuing to evolve that software.

Other systems clearly preserve institutional knowledge and skills, so this is **not yet established as unique**. The differentiator would need to be the rigor and ownership model, not merely the existence of memory.

## 11. Important architectural consequence

The deeper research reinforces one conclusion:

> AlienIntent should not build "memory" as an undifferentiated feature.

It should define **Project Cognition** as a governed domain.

Then choose or build substrates underneath it.

A Project Cognition architecture should answer:

- What object types exist?
- Which are authoritative?
- What is observation versus inference?
- What has provenance?
- Who/what may create each type?
- Who/what may modify/promote it?
- How are contradictions represented?
- How are superseded facts handled?
- How is confidence represented?
- How is retrieval scoped?
- What belongs to the project versus organization versus global/community learning?
- What is retained after model/provider replacement?
- What evidence justifies creation of a skill/specialist/tool?

This is likely higher value than inventing another vector-memory store.

## 12. Implications for the Director

The research supports retaining a permanent Director/Coordinator capability.

8090's Unified Agent and OpenVibely's project-aware persistent orchestration both reinforce the value of an intelligence layer above bounded coding workers.

AlienIntent's Director should eventually receive:

- Project Cognition APIs;
- bounded authoritative objects;
- structured planning/proposal schemas;
- factory state;
- provider-performance evidence;
- architecture/authority context.

The Director remains replaceable at the model level.

AlienIntent owns the Director identity and cognition.

## 13. Implications for skills

Skills are clearly an established mechanism.

8090 has versioned project skills.

OpenVibely curates reusable skills.

Compound Engineering compounds learnings into reusable skills/docs.

Socratic-SWE derives structured skills from solving traces.

Therefore AlienIntent should treat skills as a **standard cognitive artifact type**, not as a novel concept.

Potential AlienIntent distinction:

- skills have provenance;
- skills cite supporting trajectories/evidence;
- skill effectiveness is measured;
- promotion is governed;
- ineffective skills can be demoted/retracted;
- skills remain provider-neutral where possible.

## 14. Research-backed strategic thesis

A defensible current formulation is:

> **AlienIntent is an open, provider-neutral software factory designed to convert authorized requirements into verified software while building and governing the project-owned cognition, evidence, and specialized capabilities needed to improve how that software is understood and evolved over time.**

Do not append "first", "unique", or equivalent novelty language.

The broader category is already emerging.

AlienIntent's value must come from execution quality and architectural rigor.

## 15. Commercial interpretation

The contract-manufacturing idea remains plausible:

> **Provide authorized requirements; receive verified software.**

Potentially, for projects large or complex enough to justify it, delivery also includes a project-owned cognitive asset:

- requirements;
- architecture;
- decisions;
- evidence;
- trajectories;
- reusable skills;
- operational knowledge;
- project-specific intelligence.

This could become a meaningful commercial distinction from ordinary outsourced development.

But 8090 demonstrates that institutional knowledge preservation is already being productized, so the commercial differentiation must be sharper than "we preserve project knowledge."

Possible stronger proposition:

> **The customer receives software plus a vendor-neutral, auditable cognitive operating system for continuing to evolve it.**

This requires substantial future validation.

## 20. Bottom line

The high-level idea is not new.

That is useful information, not a negative result.

The market and research communities are validating nearly every major ingredient:

- software factories;
- project memory;
- requirements/architecture/work traceability;
- skills;
- persistent orchestrators;
- multi-provider agents;
- continuous learning;
- trace-derived specialization.

AlienIntent should therefore compete on the **quality of the integrated system**:

> rigorous authority, deterministic execution, verifiable requirements, project-owned cognition, evidence-based specialization, and continuously improving factory yield.

The project's task is no longer to prove that the category makes sense.

It is to build a substantially better implementation of the category.
